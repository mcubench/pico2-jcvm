## Highest-priority new finding: CAP and filesystem flash regions overlap

**Source-confirmed, untested failure mode.** `src/cap_store.cpp` places eight
CAP slots at `0x100000`, each `0x11000` bytes, so the CAP region is
`[0x100000, 0x188000)`. `src/choupi_pico2.cpp` places two filesystem snapshots
at `[0x100000, 0x140000)` and `[0x140000, 0x180000)`. Both complete filesystem
slots therefore overlap the CAP region: `0x80000` bytes in total. CAP LOAD
erases an entire `0x11000` slot; filesystem sync erases the selected snapshot
slot. Either operation can erase the other's records. The filesystem's static
assert still compares against the former CAP boundary `0x1c0000`, so it does
not detect the new layout. The CAP-side assert checks only the device end.
This overlap was introduced by the multi-package CAP layout recorded in
`progress.md` under 2026-10-20, commit `9c7b9ae`; it is present in that
commit as well as the current worktree. No observed physical corruption is
claimed here, but successful ordinary APDUs and power cycles cannot establish
that the regions are safe under later writes.

The configured ARM build uses `PICO_FLASH_SIZE_BYTES=2097152`. Reserving the
first 1 MiB for firmware leaves 1 MiB; eight 68 KiB CAP slots plus two 256 KiB
filesystem snapshots require `0x108000`, exceeding that budget by `0x8000`
even if the regions are packed without gaps. **Resolve this before another
CAP/FS write or firmware flash intended for continued use.** Define one shared
flash-layout header, choose a capacity that fits the actual device (for
example, fewer CAP slots or smaller per-slot capacity), and assert pairwise
non-overlap and image bounds in both ARM and RISC-V builds. Plan migration of
existing CAP and filesystem contents before changing addresses; do not treat a
fresh build as a migration. Add a single fake-flash integration test that loads
a CAP, commits filesystem state, restarts, and checks that each remains intact
after writes to every CAP slot. The existing filesystem power-cut harness
stubs `cap_store_initialize()` and cannot detect this overlap.

## Remaining order of work

1. Correct and migrate the flash layout; add pairwise compile-time assertions
   and a combined CAP/filesystem fake-flash test. Preserve existing card data
   or explicitly document a recovery/migration procedure before any physical
   update.
2. Add durable cross-store recovery and cut-point tests for CAP LOAD, INSTALL,
   and DELETE. Keep the old-or-new state invariant across process restarts.
3. Retain focused distinct-instance-AID and SELECT/GET RESPONSE regressions in
   the repository, then verify both paths on the physical reader after the
   storage fix. Validate CAP3 instance records on read.
4. Resume the unresolved Shareable APDU diagnosis and multi-package
   coexistence tests. AC1 Windows GPPro validation and the plan's three
   consecutive clean-flash integration passes remain open. Extended APDUs,
   real T=1 wait-extension signaling, and a complete multi-applet context
   model remain outside the currently verified profile.

Any subsequent platform-independent implementation must pass both
`./tools/build arm` and `./tools/build riscv` before flashing, followed by a
finite serial capture and failure-marker inspection. Use the required
host-access execution path from the first USB/PCSC operation. No hardware or
network operation was needed for this review.
