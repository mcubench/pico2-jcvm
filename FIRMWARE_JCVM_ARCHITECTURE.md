# Firmware OS & Java Card VM — Architecture and Code Navigation Guide

**Layering review updated 2026-10-24.** This describes the current checkout,
including pre-existing uncommitted changes. Sections 1–4 map implementation;
sections 5–9 assess responsibility boundaries and propose refactoring. Findings
come from source and build-definition inspection, not a new hardware test.
The required direction is native C++ Java Card API behavior and cryptography,
reached through API dispatch. Existing interpreted API providers described below
are current implementation debt, not the recommended architecture.

## 1. System Architecture & Boot

**Active hardware target:** Raspberry Pi Pico 2, RP2350 Cortex-M33 (`rp2350-arm-s`). The RISC-V (`rp2350-riscv`) build compiles the portable VM and a smoke image; the full `pico2_choupi` target is guarded by `PICO_PLATFORM STREQUAL "rp2350-arm-s"` in `CMakeLists.txt`. The checked-in `choupi/os/` Rust OS, STM32 sources/linker scripts, and `choupi/src/main_arm.cpp` belong to an older STM32 path; they are **not** linked into this Pico image. There is no RTOS scheduler in the active image.

```text
RP2350 ROM boot → Pico SDK startup/linker/stdio/TinyUSB
  → src/choupi_pico2.cpp:main_arm (single polling loop)
    ├─ src/ccid_device.cpp → GP/SCP03 + CAP install/selection
    ├─ src/choupi_pico2.cpp + src/cap_store.cpp → flash services
    └─ choupi/src/main.cpp → Context/JCRE → Interpretor
         ├─ CAP bytecodes + generated ROM-mask Java APIs
         └─ generated JNI table → native C++ → Pico SDK/mbed TLS
```

The Pico SDK supplies the actual reset vector, C runtime, and linker script through `pico_sdk_init()` and `pico_add_extra_outputs()`; this repository does not define an RP2350 `Reset_Handler`. `main()` in `choupi/src/main.cpp` calls `src/choupi_pico2.cpp:main_arm()`. That function initializes USB stdio, calls `fs_init()` (CAP store and two-slot filesystem recovery), enables a 15-second watchdog, then calls `runtime(STARTING_JAVACARD_PACKAGE, STARTING_JAVACARD_CLASS, STARTING_JAVACARD_METHOD)`. The Pico consumes the ROM mask and native-dispatch header generated by the **PC** branch of `choupi/CMakeLists.txt`; that branch selects `fr.gouv.ssi.starter.Starter.runVPCD()`, an empty startup entry because card management is native. The older STM32 branch selects `Starter.run()`, which initializes the Java GlobalPlatform registry. These entries must not be conflated. The ROM mask is embedded via `src/choupi_rommask.S.in`.

After startup, one loop calls `tud_task()`, `choupi_ccid_task()`, and `watchdog_update()`. USB endpoint callbacks queue work; `src/ccid_device.cpp:process_message()` runs APDU work in the loop, not the USB IRQ. Java runs synchronously until an interpreter entry returns. The VM's applet/context firewall checks are software checks (`choupi/src/jc_config.h`), not evidence of MPU or TrustZone separation in the active image. SCP03 authenticates selected card-management commands in native code; it is separate from Java applet isolation. No certification or complete Java Card version conformance is established here.

## 3. Execution Flows & Design Decisions

**Boot to applet readiness.** RP2350 ROM → Pico SDK reset/C runtime → `main` → `main_arm` → `fs_init` → `runtime` → `Interpretor::run` → generated `Starter.runVPCD` entry. `fs_init` verifies the reserved flash layout, initializes CAP slots, and restores the newest valid filesystem snapshot. Reader power-on calls `CapLoadSession::restoreInstalled`, which attempts pending INSTALL recovery; an instance is restored for selection through `restoreInstalledForAid` and `choupi_vm_restore_applet`. Startup does not continuously run an applet. A fresh GP INSTALL calls `runtime_install_method` and records the registered applet instance.

**APDU round trip.** TinyUSB receives CCID XfrBlock; `driver_xfer` queues it and `choupi_ccid_task` calls `process_message`. Native code handles GP/SCP03 commands first. SELECT by AID restores an installed instance, invokes `choupi_vm_select_applet`, then passes SELECT itself to `choupi_vm_process_applet`. Ordinary commands go directly there. It calls `parse_short_apdu`, fills a Java byte-array APDU buffer, creates/reuses the APDU object, and invokes applet `process` through `Interpretor::run`. `Context` tracks incoming/outgoing APDU lengths and response bytes; framework `APDU` methods enter `jni.cpp`. The wrapper adds SW, supports `61xx`/GET RESPONSE chaining, and `process_message` sends a CCID response after `fs_sync`. `ISOExceptionStatusWord` can propagate its SW; invalid transport/uncaught failures commonly become `6700`/`6F00`. The interpreter records opcode, PC and exception metadata for diagnostics. A native no-selection sentinel `0xFFFF` is handled by the CCID layer.

**AES CBC example, current implementation.** `Cipher.getInstance` selects generated `CipherProvider`; `KeyBuilder.buildKey` selects generated `KeyBuilderProvider`. `KeyProviderBase` owns Java key bytes; `clearKey` explicitly overwrites its array. `SymmetricCipherProvider` copies key bytes on `init` and implements mode checks, buffering, IV evolution, and padding in interpreted methods. Its bridge enters `native_cipher.cpp`, which checks VM arrays and calls `native_aes_cbc.cpp`/`mbedtls_aes_crypt_cbc`. This path uses software AES. Native errors become VM exceptions while provider methods also produce Java Card exception reasons. Temporary native vectors do not establish a uniform secret-zeroization policy. SCP03 has a separate native AES/CMAC path in `src/scp03.cpp`. The algorithm primitive is native, but the complete API behavior currently is not.

**Memory and NVM.** Each `Context` owns a `Stack` of 16-bit Java words and `Frame` descriptors, plus a `Heap` of stable-slot `shared_ptr` arrays/instances. `jref_t` is a compact 16-bit handle, not a raw address; bytecodes resolve it through the current heap. `bc_new` resolves a CAP constant-pool class then calls `Heap::addInstance`. Transient arrays carry `CLEAR_ON_RESET`/`CLEAR_ON_DESELECT` events and are cleared on power-on/deselection. Persistent fields/arrays are tagged records managed by `FlashMemory_Handler`, with object graph aliases; writes enter the RAM filesystem overlay. `fs_sync` writes a generation/CRC-checked snapshot to the alternate flash slot using `flash_safe_execute`, providing reset recovery for completed snapshots at the cost of erase/program wear and APDU latency. Java transaction begin takes per-tag before-images; abort restores them, commit calls `fs_sync`. The reported commit capacity is currently zero, so do not infer full Java Card transaction semantics. Pico collects unreachable VM objects after an APDU only when the typed root walk succeeds; stable handles are preserved during interpreter/native calls. VM firewall checks are compiled in, but there is no demonstrated hardware memory domain per applet.

**Consequential decisions (rationale where known).** (1) Pico SDK and repository C++ services replace the older Rust/STM32 OS on Pico. (2) One polling context owns USB and synchronous VM work, simplifying endpoint ownership while making long calls affect transport latency. (3) Host Java compilation and conversion produce JCA; the ROM-mask generator constructs **Java Card CAP components** in memory and embeds them with indexed native calls. `.class` files are host intermediates; the Pico does not execute standard JVM `.class` bytecode. (4) Stable 16-bit handles and software checks provide VM object identity and context separation. (5) Snapshots, before-images, CAP header mirrors, and the INSTALL journal provide distinct recovery mechanisms. (6) Capability selection currently changes interpreted providers, native modules, ABI mappings, and image size together. (7) AES uses software mbed TLS while SHA-256 and random use Pico facilities. These are observed choices and trade-offs, not proof of complete isolation or conformance.

## 4. Developer Navigation & Debugging

For an APDU failure, follow `process_message` → `choupi_vm_process_applet` → `Interpretor::run` → `Bytecodes::decode`; compare `CHOUPI:SELECT_*`, `CHOUPI:APDU_PROCESS`, and `CHOUPI:VM_RUNTIME_FAILURE` with SW. For native calls, inspect generated `build/arm/choupi-generated/jni.hpp` indices and `bc_impdep1`, then the matching function in `jni.cpp`/`native_*.cpp`. For bad references or exhaustion, inspect `Heap::getArray/getInstance`, `Stack::push_Frame`, `Context::visitRootReferences`, and post-APDU GC summaries (`CHOUPI_DEBUG_HEAP_GC`). For persistence, trace `FlashMemory_Handler::setPersistentField_*` → `fs_write` → `fs_sync`, then slot generation/CRC and `cap_store.cpp` for CAP metadata. For crypto, distinguish provider rejection from native mbed TLS/Pico status and remember key copies. Physical debugging is through finite CDC logs and SWD/GDB if attached; this repository's active validation path is `./tools/build arm`, `./tools/build riscv`, then authorized `./tools/cycle choupi` for the full ARM runtime and `./tools/monitor --seconds 8`. `cycle arm` and `cycle riscv` select smoke images. PC VPCD tests support APDU tracing without flash wear. The 15-second watchdog and synchronous flash/VM work can reset a stalled session; a timed-out INSTALL reports `6400`.

**Top 10 files/functions to read first**

1. `CMakeLists.txt` — establishes active ARM target, dependencies and generated assets.
2. `src/choupi_pico2.cpp:main_arm` — shows initialization and the polling loop.
3. `src/ccid_device.cpp:process_message` — identifies the native APDU routing boundary.
4. `choupi/src/main.cpp:runtime` — enters Java startup.
5. `choupi/src/main.cpp:choupi_vm_process_applet` — bridges APDUs into applet `process`.
6. `choupi/src/interpretor.cpp:Interpretor::run` — fetch, execute and error handling.
7. `choupi/src/jc_bytecodes/bytecodes.cpp:Bytecodes::decode` — opcode dispatch map.
8. `choupi/src/jc_bytecodes/bc_others.cpp:bc_impdep1` — generated JNI entry.
9. `choupi/src/heap.cpp:Heap::addInstance` — object handles and lifetime.
10. `choupi/src/jc_handlers/flashmemory.cpp:FlashMemory_Handler` — persistence and transactions.

**Five architectural traps:** (1) STM32/Rust OS code is present but absent from the Pico link. (2) RISC-V builds do not exercise the full CCID/JCVM firmware image. (3) Editing generated `jni.hpp` or provider output loses changes on rebuild. (4) `jref_t` offsets are context-local handles, not flash addresses. (5) A successful Java field write may still fail at `fs_sync`; commit capacity zero and software transactions deserve explicit testing.

**Three exploration exercises:** (1) Send SELECT then one applet APDU through CCID and PC VPCD; compare their card-session, interpreter, and response transitions. (2) Trace AES CBC `Cipher.doFinal` through `SymmetricCipherProvider`, `bc_impdep1`, generated JNI and `mbedtls_aes_crypt_cbc`; record each key copy. (3) Install an applet holding a byte array, trace `bc_new`/`Heap::addInstance`, field serialization, `fs_sync`, and reset restoration; compare the two filesystem slot generations.

## 5. Responsibility boundaries

“OS” has three meanings here: the historical Rust `choupi/os` project; the
active native services that make the Pico runtime usable; and the broader
Java Card operating environment. They are not interchangeable. The active
Pico has native OS responsibilities without a separately linked OS kernel or
an RTOS. The PC emulator still uses Rust OS services, so its platform stack
differs from the board's. On Pico, an `extern "C"` filesystem call is an
ordinary native call; its historical FFI name does not imply a syscall or
privilege transition.

| Layer | Responsibilities it should own | Responsibilities it should not own |
|---|---|---|
| RP2350 hardware and external flash | Execute native instructions; provide SRAM, flash access, interrupts, timers, USB peripheral, SHA hardware, and device facilities. | CAP parsing, Java objects, AIDs, transactions, APDU semantics, or automatic applet isolation. |
| Board support / HAL | Translate platform operations: startup, flash erase/program/read, safe XIP coordination, USB transfers, monotonic time, reset/watchdog registers, random-source access. Describe geometry and failures. | Package registry, object-field tags, Java exception reasons, SELECT policy, or deciding when an installation becomes durable. |
| Native OS services | Resource budgets, storage records, recovery, scheduling/event-loop policy, execution deadlines, diagnostics, and secure resource lifetime. | Bytecode meaning or applet-specific logic. A tagged store need not understand CAP class indexes. |
| Card runtime / JCRE and card manager | Selection, lifecycle, channels, applet identity, firewall/context policy, transient clearing, transaction semantics, GP authorization, LOAD/INSTALL/DELETE orchestration. | USB endpoint state, physical erase commands, or implementing bytecode instructions. |
| JCVM execution engine | CAP structures and linking, bytecode execution, frames, reference/type checks, exception propagation, heap and GC mechanics. | Device registers, reader-specific framing, GlobalPlatform command policy, or crypto padding implemented as instruction handlers. |
| Native Java Card API and crypto services | API method behavior, key/cipher/digest state, validation and Java Card errors; marshal VM values; invoke native cryptographic backends. | Reimplementing API behavior in generated Java providers, bypassing context checks, or changing upstream test CAPs. |
| Installed applets | Application data and decisions through the supported Java Card API. | Flash geometry, platform pointers, native backend selection, or unrestricted access to another applet's state. |

JCRE, the interpreter, and native APIs collaborate rather than forming a
strict call stack. A native API needs checked access to VM objects; the JCRE
enters the interpreter for lifecycle methods; persistent object serialization
bridges the heap and storage. These are legitimate interfaces if ownership,
errors, and lifetime are explicit.

The desired runtime command path is:

```text
USB HAL / CCID framing ─┐
                       ├→ shared card session / GP router → JCRE → JCVM
Host VPCD framing ──────┘                                  ↘ native API
                                                            ↓
                           storage / crypto / execution services
                                                            ↓
                                      Pico or host platform backend
```

Build tooling belongs outside that runtime graph. It may generate CAP metadata,
link maps, capability tables, and native bindings; generating executable API
providers currently crosses the required implementation boundary.

## 6. Findings: separation that needs improvement

L3 is the required native-API compliance change. L2 and L5 are the main
cross-cutting correctness refactors; L1, L4, and L6 provide their service
boundaries. L7–L10 make lifecycle, compatibility, crypto resources, and build
coverage enforceable. These priorities concern architecture, not a claim
that every listed coupling currently causes an observed failure.

### L1 — Board integration also implements storage and VM policy

[`src/choupi_pico2.cpp`](src/choupi_pico2.cpp) combines startup, USB polling,
watchdog scratch registers, flash snapshots, migration, RAM overlay allocation,
Java object-field path construction, memory accounting, CAP-store adapters,
and detailed interpreter diagnostics. `path_applet_field16` knows Java
serialization identity; `write_filesystem_snapshot` knows physical erase and
program operations. These belong on different sides of the platform boundary.

Split board startup/HAL from a portable record store, snapshot codec, migration
service, and VM persistence schema. Keep one flash-geometry interface below
both CAP storage and filesystem storage. Preserve the existing shared
[`flash_layout.hpp`](src/flash_layout.hpp) as the authority for reservations;
do not reproduce addresses in each extracted module. This is extraction of
responsibilities, not a reason to introduce an RTOS.

### L2 — CCID framing owns too much of the card operating environment

[`ccid_device.cpp:process_message`](src/ccid_device.cpp) handles USB reader
messages and also owns `Scp03Session`, `CapLoadSession`, registry pagination,
GP routing, SELECT/deselect decisions, applet restoration, and persistence
flushes. [`main_pc.cpp`](choupi/src/main_pc.cpp) independently implements
similar card-management behavior around VPCD.

Extract a transport-independent card session with command, reset, and
power-off operations. CCID should validate framing, deliver an APDU, and frame
the result. VPCD should call the same session. Keep SCP03 authorization in
the card manager, ahead of privileged mutations; keep USB errors distinct
from Java Card status words. Existing `gp_*.hpp`, `short_apdu.hpp`, and
`vpcd_session.*` provide useful partial seams.

### L3 — Native primitives are wrapped in substantial interpreted API behavior

[`tools/javacard-support.py`](tools/javacard-support.py) generates providers
from [`tools/java-support/`](tools/java-support). For example,
`SymmetricCipherProvider` owns buffering, padding, IVs, initialization, and
key copies; `RSACipherProvider` buffers inputs and extracts key components;
`MbedTlsDigestProvider` accumulates input in a fixed-size Java array.
These are API implementations even though the final primitive runs in C++.

This conflicts with the required native runtime boundary. Move API state and
behavior into native C++ dispatch, including constructors/factories, update/
final state machines, key lifecycle, validation, and exception reasons.
Retain the API class/export metadata needed to link upstream CAPs; do not
remove the ROM mask merely because its build uses Java intermediates.
Replace provider-generation responsibilities with native binding/capability
metadata. Existing upstream CAPs remain unchanged test inputs.

Native state needs an explicit lifetime model: associate it with a checked
VM object and owning context, release it during GC/deletion, clear it on the
specified reset/deselect events, and serialize only permitted persistent
state. Never persist a raw C++ pointer. A successful one-shot vector does not
validate these lifecycle requirements.

### L4 — Platform dependencies reach inside nominally portable VM code

[`Interpretor::run`](choupi/src/interpretor.cpp) calls watchdog, clock, and
INSTALL-trace hooks under `#ifndef PC_VERSION`. Class resolution and heap
allocation similarly emit board diagnostic stages. Native random, SHA-256,
and RSA files directly select Pico SDK versus host implementations. The RSA
cipher module even supplies Mbed TLS's global millisecond-clock hook.

These function hooks are already a useful seam, but `PC_VERSION` combines
platform selection, diagnostic policy, execution budgets, and backend choice.
Introduce explicit platform/execution services with host implementations:
clock, watchdog progress, cancellation/deadline, entropy, hardware hashing,
and trace sink. Put Mbed TLS platform hooks in platform support, rather than
an optional algorithm module. VM code should emit semantic events, not know
which watchdog scratch word stores them.

### L5 — Persistence has recovery mechanisms but no single coordinating owner

Current improvements must be retained:
[`cap_store.cpp`](src/cap_store.cpp) alternates generation/CRC-protected CAP
metadata headers with mirrors; the filesystem alternates snapshots;
[`cap_load.cpp`](src/cap_load.cpp) commits an INSTALL journal before publishing
the CAP instance entry and supports replay. This is more than simple
in-place metadata rewriting.

However, orchestration spans `CapLoadSession`, `FlashMemory_Handler`, the
board overlay, and CAP storage. `finishLoad` writes CAP storage before its
filesystem transaction; DELETE commits filesystem changes before updating
CAP metadata. Those orders require explicit recoverable intermediate states.
This is a source-confirmed coordination concern, not a claim that every
interruption currently loses data.

More fundamentally, board `fs_sync()` returns success without flushing while
the VM transaction is active; `commitPersistentWriteTransaction()` clears
that flag and calls `fs_sync()` again. A lower storage service therefore
queries higher VM state, and “success” depends on hidden transaction context.

Define a lifecycle transaction coordinator and explicit prepare, durable
commit, publish, and recovery contracts for LOAD/INSTALL/DELETE. Keep Java
object encoding in VM persistence and flash mechanics in the backend. Test
each durable boundary using the real shared storage implementation and
simulated power cuts, including journal-clear failure and repeated recovery.

### L6 — The service ABI is inherited, scattered, and weakly specified

[`choupi/os/src/ffi.h`](choupi/os/src/ffi.h) mixes flash access, filesystem
records, Java field paths, remote calls, and emulator functions. Pico supplies
its own implementation of part of this historical Rust-facing ABI; additional
`extern "C"` declarations are repeated in transport, VM, and persistence files.
`fs_sync` and newer CAP services are not a single coherent contract there.

Create shared, focused headers for record storage, package images, runtime
entry/results, platform services, and diagnostics. Specify pointer ownership,
length units, mapping lifetime, thread/context restrictions, and durability.
Distinguish absent records, corrupt data, capacity exhaustion, and I/O failure
internally; translate those results into status words or Java exceptions at
the appropriate boundary. A C ABI is acceptable; scattered declarations and
ambiguous boolean/integer conventions are the problem.

### L7 — Object identity, session state, and resource budgets need clearer owners

[`Context`](choupi/src/context.hpp) owns heap, frames, applet roots, and APDU
objects, while [`main.cpp`](choupi/src/main.cpp) owns a global selected context,
selection flags, and a global pending response chain. That models the current
single selected execution context; it is not by itself a per-channel or
cross-applet runtime model. Likewise, `jref_t` values are context-local handles,
not globally meaningful object IDs or hardware memory domains.

Give a card session ownership of channel/selection/response state and give
the JCRE ownership of context transitions and object access checks. Keep GC
root enumeration and native-object lifetime coordinated. Define native
scratch-memory budgets separately from Java persistent/transient quotas:
current Pico memory reporting uses allocator free space and stack limit,
while persistent availability reports overlay capacity. These are useful
estimates, not a unified allocation guarantee. Zero reported transaction
capacity also needs reconciliation with the implemented transaction service.

### L8 — Export compatibility policy is distributed through linking and execution

Class/interface token generation exists in
[`javacard-class-tokens.py`](tools/javacard-class-tokens.py), but method,
constructor, interface, and inheritance remapping also lives in
[`jc_cp.cpp`](choupi/src/jc_handlers/jc_cp.cpp),
[`jc_class.cpp`](choupi/src/jc_handlers/jc_class.cpp), and invocation handlers.
Thus an API-profile change can affect class identity, dispatch, and exception
matching across several layers. Class and interface token namespaces must
remain distinct even when their numeric values overlap. A storage CRC checks
byte integrity; CAP structural validation, import compatibility, and execution
safety remain loader/VM responsibilities. They are not supplied by flash
hardware or metadata checksums.

Treat this as a versioned API linkage contract. Generate mappings from export
identity and method descriptors where possible; centralize unavoidable
compatibility rules. Resolve imported symbols consistently before execution,
without removing runtime receiver/type checks. Validate mappings across
profiles using unchanged upstream CAPs, including inherited methods,
constructors, interfaces, and caught exceptions. Do not make bytecode handlers
accumulate algorithm-specific token exceptions.

### L9 — Crypto backends lack a consistent platform and secret-lifetime boundary

SCP03 supplies its own AES/CMAC and random-source selection, while applet
crypto uses separate native files. Randomness is obtained independently in
SCP03, RandomData, and RSA; SHA-256 directly chooses hardware versus software.
The global zeroization hook resides in SCP03, while temporary key vectors and
provider arrays have different clearing behavior.

Extract shared primitive/platform backends for entropy, AES, hashes, timing,
and secure clearing. Keep SCP03 keys, sessions, and authorization policy
separate from applet-owned cryptographic state. Use bounded buffers and
explicitly wiped secret containers; do not equate ordinary vector destruction
with clearing. The HAL can expose a random source or hardware hash operation;
API conformance, algorithm selection, and error translation remain native
runtime responsibilities.

### L10 — Build targets and emulator behavior do not enforce the advertised layers

[`CMakeLists.txt`](CMakeLists.txt) builds `choupi_vm_core` with Pico-oriented
headers, optional crypto, and legacy ABI includes. The full CCID firmware is
ARM-only; a RISC-V wrapper pass compiles VM objects and a smoke image, not
equivalent full-runtime firmware. The Pico also consumes shared
`build/choupi-pc` ROM-mask/JNI outputs: even its startup selection currently
comes from the PC generation branch. Hash checks are useful existing
protection, but this is still cross-target artifact ownership.

Separate architecture-neutral API metadata generation from host executable
building. Isolate generated outputs by capability profile and ABI version;
bind firmware to an explicit manifest and startup policy. Capability-selection
tables must also be distinguished from measured conformance results. Define build
targets for VM, native APIs, card runtime, storage, and each platform backend,
then enforce allowed includes/dependencies.

The host CAP backend in `main_pc.cpp` still models one package and one stored
instance, unlike Pico's eight slots and per-package instance records. Share
the storage/session logic and vary the block-device backend. Otherwise a host
pass cannot establish multi-package coexistence or equivalent reset recovery.

## 7. Execution and trust boundaries

The meaningful protection boundary currently is checked interpreter/native
dispatch within one native process. The legacy Rust MPU/context code is not
evidence that active Pico applets receive MPU or TrustZone domains. Hardware
isolation would be a separate design requiring native-call, peripheral, flash,
and exception-path containment; moving files into a HAL does not create it.

The polling loop owns TinyUSB/CCID endpoint state; keep that existing ownership
rule during extraction. Synchronous interpreter or crypto calls prevent the
loop from servicing another request. Refreshing the watchdog on every opcode
detects a stuck native operation differently from an applet that executes an
endless bytecode loop. Method-offset execution currently has a five-second
check, but there is no general cooperative scheduling contract covering all
native work. Define per-command budgets and cancellation/safe-point behavior
before introducing reentrancy or more execution contexts.

Diagnostics must describe their scope. `main_arm` repeats `TEST:PASS` based on
the startup status captured before the polling loop; that heartbeat does not
prove each later APDU, algorithm, or storage operation passed. Preserve boot,
transport, VM, storage, and known-answer-test outcomes separately. Include
execution identity and failure stage without exposing keys or secret input.

## 8. Refactoring order and completion criteria

1. **Make contracts visible.** Add focused interfaces and dependency targets;
   identify owners for card session, object persistence, native API state,
   and platform resources. Preserve current on-flash formats and capture
   existing APDU behavior before moving implementations.
2. **Unify transport-independent behavior.** Extract native GP/APDU routing
   and lifecycle policy from CCID and VPCD. Test identical command/reset
   sequences through both transports; retain protocol-specific framing.
3. **Separate durable storage.** Extract overlay/snapshot and CAP repositories
   over a shared flash/block backend. Centralize lifecycle recovery, retaining
   metadata mirrors and the INSTALL journal. Cover crash boundaries and
   migration with the same stores on fake flash and hardware.
4. **Move API behavior to C++.** Migrate a vertical API slice, including its
   state and errors, into native dispatch. Keep export compatibility and
   upstream CAP bytes stable. Test update/final, reset/deselect, GC, persistence,
   and memory exhaustion before migrating further families.
5. **Enforce platform independence.** Move clock, entropy, watchdog, crypto
   acceleration, and Mbed TLS hooks into explicit backends. Make generation
   profile-specific and expand host storage parity. Report ARM full-runtime
   and RISC-V compile/smoke coverage accurately.

Completion means the portable engine needs no Pico headers; transports share
one card policy; storage never asks the interpreter whether it may flush;
native API semantics have one C++ owner; and profile generation cannot
silently change ABI/startup policy for another target. Use dependency checks,
native unit tests, shared-backend fault injection, and unchanged upstream CAP
tests to enforce these boundaries. Physical changes still require both
architecture builds and the repository's authorized flash/finite-log workflow.

## 9. Overall assessment

The repository has useful seams already: checked VM references, filesystem
functions, pure protocol helpers, native cryptographic primitives, shared flash
layout, metadata mirrors, and recovery journals. Its main weakness is that
policy and mechanism cross those seams repeatedly. The highest-value changes
are a shared card-runtime/session layer, an explicit durable-storage coordinator,
and native C++ ownership of API behavior. Preserve the working recovery and
compatibility mechanisms while making those owners independently testable.
