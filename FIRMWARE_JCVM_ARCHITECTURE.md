# Firmware OS & Java Card VM — Architecture and Code Navigation Guide

## 1. System Architecture & Boot

**Active hardware target:** Raspberry Pi Pico 2, RP2350 Cortex-M33 (`rp2350-arm-s`). The RISC-V (`rp2350-riscv`) build compiles the portable VM and a smoke image; the full `pico2_choupi` target is guarded by `PICO_PLATFORM STREQUAL "rp2350-arm-s"` in `CMakeLists.txt`. The checked-in `choupi/os/` Rust OS, STM32 sources/linker scripts, and `choupi/src/main_arm.cpp` belong to an older STM32 path; they are **not** linked into this Pico image. There is no RTOS scheduler in the active image.

```text
RP2350 ROM boot → Pico SDK startup/linker/stdio/TinyUSB
  → src/choupi_pico2.cpp:main_arm (single polling loop)
    ├─ src/ccid_device.cpp → GP/SCP03 + CAP install/selection
    ├─ src/choupi_pico2.cpp + src/cap_store.cpp → flash services
    └─ choupi/src/main.cpp → Context/JCRE → Interpretor
         ├─ CAP bytecodes + generated ROM-mask Java APIs
         └─ generated JNI table → native C++ → Pico SDK/mbed TLS
```

The Pico SDK supplies the actual reset vector, C runtime, and linker script through `pico_sdk_init()` and `pico_add_extra_outputs()`; this repository does not define an RP2350 `Reset_Handler`. `main()` in `choupi/src/main.cpp` calls `src/choupi_pico2.cpp:main_arm()`. That function initializes USB stdio, calls `fs_init()` (CAP store and two-slot filesystem recovery), enables a 15-second watchdog, then calls `runtime(STARTING_JAVACARD_PACKAGE, STARTING_JAVACARD_CLASS, STARTING_JAVACARD_METHOD)`. The generated indices in `build/arm/choupi-generated/jni.hpp` point to `fr.gouv.ssi.starter.Starter.run()`, which initializes the Java GlobalPlatform registry. The ROM mask is generated by `choupi/CMakeLists.txt`/`tools/build-pc` and embedded via `src/choupi_rommask.S.in`.

After startup, one loop calls `tud_task()`, `choupi_ccid_task()`, and `watchdog_update()`. USB endpoint callbacks queue work; `src/ccid_device.cpp:process_message()` runs APDU work in the loop, not the USB IRQ. Java runs synchronously until an interpreter entry returns. The VM's applet/context firewall checks are software checks (`choupi/src/jc_config.h`), not evidence of MPU or TrustZone separation in the active image. SCP03 authenticates selected card-management commands in native code; it is separate from Java applet isolation. No certification or complete Java Card version conformance is established here.

Hardware dependence ends primarily at `src/choupi_pico2.cpp`, `src/ccid_device.cpp`, `src/cap_store.cpp`, and Pico branches in `choupi/src/native_*.cpp`. The portable C++ interpreter calls an `ffi.h` filesystem interface and generated JNI methods. `jc_cap/` describes serialized CAP structures; `jc_handlers/` resolves CAP components/imports and persistent tags. `choupi/src/main.cpp` is also portable JCRE glue, despite its name. `build/*/jni.hpp`, generated Java provider sources, and the ROM-mask `flash` image are outputs: change their inputs, not generated copies.

## 3. Execution Flows & Design Decisions

**Boot to applet readiness.** RP2350 ROM → Pico SDK reset/C runtime → `main` → `main_arm` → `fs_init` → `runtime` → `Interpretor::run` → `Starter.run` → GlobalPlatform Java registry. `fs_init` verifies the reserved flash layout, initializes CAP slots, and restores the newest valid filesystem snapshot. Installed applets are restored for selection later by `CapLoadSession::restoreInstalledForAid` and `choupi_vm_restore_applet`; startup does not continuously run an applet. A fresh GP INSTALL calls `runtime_install_method` and records the registered applet instance.

**APDU round trip.** TinyUSB receives CCID XfrBlock; `driver_xfer` queues it and `choupi_ccid_task` calls `process_message`. Native code handles GP/SCP03 commands first. SELECT by AID restores an installed instance, invokes `choupi_vm_select_applet`, then passes SELECT itself to `choupi_vm_process_applet`. Ordinary commands go directly there. It calls `parse_short_apdu`, fills a Java byte-array APDU buffer, creates/reuses the APDU object, and invokes applet `process` through `Interpretor::run`. `Context` tracks incoming/outgoing APDU lengths and response bytes; framework `APDU` methods enter `jni.cpp`. The wrapper adds SW, supports `61xx`/GET RESPONSE chaining, and `process_message` sends a CCID response after `fs_sync`. `ISOExceptionStatusWord` can propagate its SW; invalid transport/uncaught failures commonly become `6700`/`6F00`. The interpreter records opcode, PC and exception metadata for diagnostics. A native no-selection sentinel `0xFFFF` is handled by the CCID layer.

**AES CBC example.** `Cipher.getInstance` selects generated `CipherProvider`; `KeyBuilder.buildKey` selects generated `KeyBuilderProvider`. `KeyProviderBase` owns a Java `byte[] keyData` in the owning applet's object graph; `setKey` copies into it and `clearKey` overwrites it with zero. `AESCipherProvider` copies key bytes into `CbcCipherProvider.keyData` on `init`; `doFinal/update` call `CbcCipherNativeBridge.cipherCbc`. Generated JNI dispatch invokes `fr_gouv_ssi_nativeimpl_CbcCipherNativeBridge_cipherCbc`, which checks types, ranges, key/IV/block sizes, copies arrays into C++ vectors, then calls `cipherAesCbc` and mbed TLS `mbedtls_aes_crypt_cbc`. No RP2350 AES accelerator is used by this path. Native errors throw VM `Exceptions::CryptoException` or `RuntimeException`; Java validation throws `CryptoException` reasons. **Sensitive-data caveat:** Java key arrays are explicitly cleared only by `clearKey`; the temporary C++ vectors have no explicit zeroization in this path. SCP03's separate native AES implementation is in `src/scp03.cpp`.

**Memory and NVM.** Each `Context` owns a `Stack` of 16-bit Java words and `Frame` descriptors, plus a `Heap` of stable-slot `shared_ptr` arrays/instances. `jref_t` is a compact 16-bit handle, not a raw address; bytecodes resolve it through the current heap. `bc_new` resolves a CAP constant-pool class then calls `Heap::addInstance`. Transient arrays carry `CLEAR_ON_RESET`/`CLEAR_ON_DESELECT` events and are cleared on power-on/deselection. Persistent fields/arrays are tagged records managed by `FlashMemory_Handler`, with object graph aliases; writes enter the RAM filesystem overlay. `fs_sync` writes a generation/CRC-checked snapshot to the alternate flash slot using `flash_safe_execute`, providing reset recovery for completed snapshots at the cost of erase/program wear and APDU latency. Java transaction begin takes per-tag before-images; abort restores them, commit calls `fs_sync`. The reported commit capacity is currently zero, so do not infer full Java Card transaction semantics. Pico collects unreachable VM objects after an APDU only when the typed root walk succeeds; stable handles are preserved during interpreter/native calls. VM firewall checks are compiled in, but there is no demonstrated hardware memory domain per applet.

**Consequential decisions (rationale where known).** (1) Pico SDK replaces the older Rust/STM32 OS; this keeps USB/flash integration local, while limiting the active full runtime to ARM. (2) One polling context runs USB and the interpreter; code comments explicitly avoid USB IRQ flash/allocation work, trading APDU latency for simpler endpoint ownership. (3) Generated ROM-mask/JNI converts Java API classes to CAP-like executable data and indexed native calls; it saves dynamic linking machinery but makes generation inputs and tokens critical. (4) Stable 16-bit handles plus per-context heaps bound reference size; cross-context validity depends on software checks. (5) Alternate flash snapshots plus transaction before-images provide reset recovery; snapshot frequency trades flash endurance and latency for persistence. (6) Capability selection omits Java providers/native modules at build time; changing `config/javacard-support.json` changes both ABI-visible implementation and image size. (7) AES CBC uses software mbed TLS, while SHA-256 and random use Pico facilities; crypto performance and error behavior vary by provider. Items 1, 4, 5 and 7 describe observed structure and inferred trade-offs; item 2 has an explicit code comment.

## 4. Developer Navigation & Debugging

For an APDU failure, follow `process_message` → `choupi_vm_process_applet` → `Interpretor::run` → `Bytecodes::decode`; compare `CHOUPI:SELECT_*`, `CHOUPI:APDU_PROCESS`, and `CHOUPI:VM_RUNTIME_FAILURE` with SW. For native calls, inspect generated `build/arm/choupi-generated/jni.hpp` indices and `bc_impdep1`, then the matching function in `jni.cpp`/`native_*.cpp`. For bad references or exhaustion, inspect `Heap::getArray/getInstance`, `Stack::push_Frame`, `Context::visitRootReferences`, and post-APDU GC summaries (`CHOUPI_DEBUG_HEAP_GC`). For persistence, trace `FlashMemory_Handler::setPersistentField_*` → `fs_write` → `fs_sync`, then slot generation/CRC and `cap_store.cpp` for CAP metadata. For crypto, distinguish provider rejection from native mbed TLS/Pico status and remember key copies. Physical debugging is through finite CDC logs and SWD/GDB if attached; this repository's active validation path is `./tools/build arm`, `./tools/build riscv`, then authorized `./tools/cycle arm` and `./tools/monitor --seconds 8`. PC VPCD tests support APDU tracing without flash wear. The 15-second watchdog and synchronous flash/VM work can reset a stalled session; a timed-out INSTALL reports `6400`.

**Top 10 files/functions to read first**

1. `CMakeLists.txt` — establishes active ARM target, dependencies and generated assets.
2. `src/choupi_pico2.cpp:main_arm` — shows initialization and the polling loop.
3. `src/ccid_device.cpp:process_message` — identifies the native APDU routing boundary.
4. `choupi/src/main.cpp:runtime` — enters Java startup.
5. `choupi/src/main.cpp:choupi_vm_process_applet` — bridges APDUs into applet `process`.
6. `choupi/src/interpretor.cpp:Interpretor::run` — fetch, execute and error handling.
7. `choupi/src/jc_bytecodes/bytecodes.cpp:Bytecodes::decode` — opcode dispatch map.
8. `choupi/src/jc_bytecodes/bc_others.cpp:bc_impdep1` — generated JNI entry.
9. `choupi/src/heap.cpp:Heap::addInstance` — object handles and lifetime.
10. `choupi/src/jc_handlers/flashmemory.cpp:FlashMemory_Handler` — persistence and transactions.

**Five architectural traps:** (1) STM32/Rust OS code is present but absent from the Pico link. (2) RISC-V builds do not exercise the full CCID/JCVM firmware image. (3) Editing generated `jni.hpp` or provider output loses changes on rebuild. (4) `jref_t` offsets are context-local handles, not flash addresses. (5) A successful Java field write may still fail at `fs_sync`; commit capacity zero and software transactions deserve explicit testing.

**Three exploration exercises:** (1) Send SELECT then one applet APDU in PC VPCD; mark every `process_message`/interpreter/response transition. (2) Trace AES CBC `Cipher.doFinal` through `CbcCipherProvider`, `bc_impdep1`, generated JNI and `mbedtls_aes_crypt_cbc`; record each key copy. (3) Install an applet holding a byte array, trace `bc_new`/`Heap::addInstance`, field serialization, `fs_sync`, and reset restoration; compare the two filesystem slot generations.
