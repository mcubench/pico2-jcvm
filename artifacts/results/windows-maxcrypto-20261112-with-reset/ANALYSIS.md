# Analysis — 2026-11-13, no implementation changes

## Finding

Most likely this combines **persistent-overlay degradation/exhaustion** with a **CCID transport stall**. The Windows evidence establishes symptoms and ordering, not a uniquely proven root cause. The leading concrete defect for the lasting resource failure is the old overlay compaction rehash bug, already reproduced independently and corrected in commit `92c91943`; the reported `580f3f40` image predates that fix. This test cannot assess the fixed image. A cleanup throughput deficit remains a plausible additional contributor.

## Exact observations

Line references below refer to the supplied `ALGTEST_LOG_pico2_maxcrypto_20261112withReset_all_log.txt`.

- 287 method headers; 3,627 responses with `9000`, 28 with `F205`, five with `6F00`, 12 with `F105`, four with `F101`. There are 1,829 adjacent reset-command / `9000` response pairs. These counts cover combined/resumed output and include retries, not distinct successfully measured algorithms. Reset acknowledgement proves command acceptance, not completed reclamation.
- First transport failure: line 21522, AES-256 ECB ISO9797 M2 `Cipher_init`, measurement `B043`, after successful baseline/measurement responses and a 375 ms reset. Next SELECT fails; subsequent reset reports `SCARD_E_SERVICE_STOPPED`. No returned memory error precedes this first stall.
- Later RSA-1984 PKCS1 preparation returns `AA9000`; five baseline invocations also return `AA9000`. The full 50-iteration measurement `B043` then loses communication at line 30056. Thus the RSA-1984 prepare dimensions are demonstrably usable before the failure.
- After reconnection, SELECT succeeds. Reset returns `9000` in 3,017 ms, but the very next preparation returns **F205 in 3,225 ms at line 30109**. A retry returns `6F00` in 3,186 ms at line 30124. Therefore resource failure precedes the first generic error, contrary to the impression from the README excerpt. Subsequent RSA-1984 preparations give `6F00`; RSA-2048 onward repeatedly gives `F205`.
- Later reset commands continue returning `9000` around 2.9–3.0 seconds; preparation failures become very slow (for example RSA-3072 ISO14888 preparation: 116,638 ms). Slow failed operations are compatible with retries, graph traversal or storage work, but host elapsed time alone cannot identify the expensive operation.
- Supplied README reports package DELETE waits 15.009 s then loses transport; after replug the applet remains listed. Firmware reupload followed by fresh install/delete succeeds. No completed DELETE status word was received: this is not evidence of a particular DELETE exception or proof that it ran out of RAM.

## Why the persistent overlay is the strongest lead

`src/pico_filesystem.cpp` limits the overlay arena to 96 KiB, with an additional serialized-index constraint; the larger flash persistence region does not imply that all of it is usable object payload. `fs_write()` compacts before rejecting a write. Importantly, **any failed compaction is translated to OUT_OF_FLASH**, not only a genuine capacity shortage. `write_persistent_tag_or_throw()` in `choupi/src/jc_handlers/flashmemory.cpp` maps status 1 to SystemException reason 5 (`F205`). F205 therefore cannot distinguish physical capacity pressure from a damaged/rejected compaction layout. Other SystemException sources exist, so the Windows SW alone does not prove this path.

The independently reproduced old rehash loop started inside arbitrary mapping paths. It could leave duplicate table entries, then overwrite a live mapping when moving its predecessor. The regression in commit `92c91943` lost tag 856 at its first compaction before the fix. Later filesystem activity can then encounter unfindable records, inconsistent serialized offsets, or a rejected compaction. A separate local D92 trace actually recorded `records_overlap` and F205 at 98,292/98,304 bytes. That exact pair was not reproduced by the regression and is corroborating evidence, not identification of the Windows on-card state.

Enabling reset/deletion can postpone accumulation while also causing more delete/compact/rehash cycles. A later threshold failure is consistent with this defect. Reinsertion drops volatile state but restores persistent data; it cannot repair an already inconsistent saved overlay or remove a real persistent backlog. An empty-card firmware reupload clears that state. Those observations favor persistent state over a purely volatile native-heap leak, while not excluding allocation failures during large graph reconstruction. Failed partial preparations can further complicate later state; 6F00 only establishes an uncaught/generic failure, not a specific corruption mechanism.

## Additional candidate: reclamation cannot keep up

`choupi/src/main.cpp::service_object_deletion_request_if_enabled()` traces retained heaps/roots then calls the persistent reclaimer with a shared maximum of **eight records per APDU** (`persistent_inventory.hpp`). Incomplete batches retain the request; incomplete root tracing can skip sweeping conservatively. A reset followed by a preparation does not guarantee sufficient space for that preparation, especially because cleanup is serviced after APDU execution. Repeated preparations and 50-iteration measurements can generate more obsolete records than intervening batches remove. A 9000 reset therefore does not refute an increasing backlog. Without erased-record counts, live/unreachable inventory and bytes-used telemetry, neither a backlog nor erroneous root retention is demonstrated by this run. Raising the budget without evidence is not justified and previously made response latency problematic.

## Communication is a separate failure axis

The first AES stall occurs before any returned F205/6F00. Independently captured local traces showed VM `9000`, final response pending, IN endpoint idle, zero submission errors, and stale `native_extension_in_flight`. That is a concrete response-delivery defect matching the Windows disappearance class; a recovery was added separately in `49a390d5`, after the reported image. Windows has no endpoint telemetry, so attribution is still a hypothesis. Slow persistence/cleanup and long RSA measurements increase exposure to time-extension handling. The Windows service errors also permit a host driver/service contribution; they do not prove a VM crash.

Uninstall traverses/deletes persistent namespaces and commits storage (`src/gp_delete.hpp::commit_delete_state`); it can encounter the same storage/latency/transport problems even when SELECT/list work. The applet still being listed is compatible with an incomplete or rolled-back transactional delete. This does not isolate cleanup RAM exhaustion. Native RSA buffers should not be resized based on these results: preparation and baseline worked, failure depends on campaign history, and persists across power cycles.

## Next discriminating evidence, no implementation proposed

Preserve the failing card before any empty-card reflash. A finite serial capture and read-only firmware/board identity would be most useful: look for `FS_WRITE_FAIL`, `FS_COMPACT_REJECT`, `PERSIST_WRITE_FAIL`, deletion counts/skip reasons and final-response endpoint state. A failing persistent snapshot would allow direct overlay validation, if an existing safe export path is available. A controlled follow-up on a separate token with the already existing compaction fix and CCID recovery would distinguish these known defects from a remaining cleanup throughput/root problem; it must retain per-device client and serial logs. No hardware command, build, test campaign, or runtime implementation was performed for this analysis. Fixture integrity verification passed for all 81 manifest inputs; it does not verify the absent Windows client binary.
