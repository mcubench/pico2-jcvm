# Code review — 2026-10-13

Scope: current worktree, recent applet lifecycle/virtual dispatch commits, generated JNI declarations, embedded ROM configuration, and the supplied JCAlgTest v1.8.2 CAP. No physical token access or firmware upload was performed. Implementation files were not changed. Host-only validation: `./tools/build arm` failed at link time; log `artifacts/logs/review-arm-build-20261013.log`.

## Findings

1. **P1 — Native declaration and definition disagree.** `choupi/src/jni.cpp:280` defines `setAPDUOutgoing(jref_t, short, short)`, but the regenerated JNI header declares/calls `setAPDUOutgoing(std::shared_ptr<JC_Array>, short, short)` for the Java `byte[]` parameter. The ARM link fails with an undefined reference to the latter signature. Match the generated ABI and preserve the correct response-buffer identity.

2. **P1 — JNI dispatch and embedded Java bytecode come from different ROM builds.** `tools/build:38` copies `build/choupi-pc/jni.hpp`, while `CMakeLists.txt:70` embeds `build/choupi-rommask/flash-algtest.bin`. Adding APDU natives changes native method indices and Java framework layout in the newly generated output; the old image still supplies the former bytecode/layout. Even after resolving the linker error, native calls can dispatch to unrelated functions and the APDU methods will remain the old stubs. Generate and consume the image/header as one matched pair.

3. **P1 — Lifecycle calls use the wrong virtual tokens for the supplied applet.** `choupi/src/main.cpp:163` requests token 7 for select, line 173 requests 5 for deselect, and line 272 requests 8 for process. Direct inspection of the v1.8.2 CAP Class component found the Applet subclass at offset 148 with public table base 4 and entries `4=0x3db5`, `5=0xffff`, `6=0x3db1`, `7=0x3e63`. Method bytes and source identify token 6 as boolean select, 4 as void deselect, and 7 as process(APDU). These calls construct internal concrete class references, so imported-reference token remapping does not fix them. SELECT instead enters process with only the receiver; process token 8 is outside the concrete table. Keep token domains distinct and translate when traversing into the ROM superclass.

4. **P1 — APDU instance allocation resolves the wrong class and wrong byte order.** `choupi/src/main.cpp:257` passes the applet's own package information to `remap_imported_class_token`, although that helper matches the imported framework AID. For JCAlgTest's package AID, token 10 stays 10 instead of mapping to framework APDU export token 7. In addition, line 260 uses `getExportedClassOffset` without the endian conversion used by `ConstantPool_Handler::getClassInformation` at line 207. Both errors feed an incorrect class index to `heap.addInstance`. Resolve through framework import metadata and convert the exported CAP offset consistently.

5. **P1 — The cached Java APDU buffer never receives the next command.** `APDU.java:294` obtains its buffer once. Generated `getAPDUBuffer` dispatch adds a deep copy to the heap (`heap.addArray(*ret)`), so the Java field refers to a different array from `Context::apdu_buffer_ref`. `main.cpp:205` refreshes only the original context array and reuses the APDU object at line 219. Consequently the second and later commands read the first command or previous response bytes. Use one shared buffer identity, or refresh the Java-visible array for every command.

6. **P1 — Error paths send an empty response without a status word.** `main.cpp:195`, 223, 251, 285 and the catch at 302 can return a status before constructing response bytes. `ccid_device.cpp:359` initializes the output length to zero, then line 364 adopts that length for every return except 6999. A malformed APDU or allocation/lookup failure therefore yields a zero-length CCID APDU instead of 6700/6F00. Define the bridge as data-plus-status or have the caller append every returned status consistently.

7. **P1 — Inherited virtual lookup keeps reading the original table.** `jc_class.cpp:336` captures the initial class table; line 341 continues using the initial `claz` and line 350 reads that same table after line 368 moves `token` to its superclass. A 0xffff inherited entry cannot resolve and can loop or fail while repeatedly walking the superclass chain. The supplied applet has just such an entry at token 5. Refresh class/table/base and translate the token domain at each superclass step. The package-method resolver has a similar stale-table pattern.

8. **P2 — A rejected selection still leaves a processable applet context.** `main.cpp:167` returns 6999 for false select without clearing `selected_applet_context`; `ccid_device.cpp:341` returns the error without cleanup. The subsequent ordinary command is dispatched by `choupi_vm_process_applet` solely because that context exists. A false/failed SELECT must leave the applet unselected, and process should require successful selection state.

## Validation limits

The build failure was reproduced without touching USB. CAP table offsets and method prefixes were inspected directly from the supplied ZIP. Runtime consequences are derived from the code and generated output; they have not been exercised against a Java applet or physical token. AC1–AC5 remain unverified as described in TODO.md. This review identifies blocking defects, not a claim that other code is correct.
