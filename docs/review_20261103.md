# Functionality review — 3 November 2026

## Assessment and review boundary

The current code has substantial working integration, but the passing support reports and existing unit suites leave important correctness gaps. This review found reproducible failures in persistent object identity, transaction visibility, reference ownership, transient lifetimes, array sizing and arithmetic. Source inspection also found unsafe CCID length handling and incomplete recovery and execution boundaries. These should be addressed before treating the current image as a dependable multi-applet Java Card platform.

Reviewed baseline: Git `6e58df36f05301b3b0a98039b00b810b78e71651`, **including the pre-existing working-tree modifications**. In particular, `heap.cpp`, `heap.hpp` and `cap_load.cpp` differ from that commit. The supplied SDK/ROM-mask submodules also have existing untracked content. Findings describe the files actually present during review; their hashes are in [reviewed-sources.sha256](../artifacts/reviews/review_20261103/reviewed-sources.sha256). Existing changes were preserved.

The review followed the active path through Pico CCID, card management, CAP storage/loading, interpreter and bytecodes, contexts and SIO, native crypto, persistent objects, filesystem transactions and host VPCD. It also inspected the generated native dispatch and framework sources consumed by that path. Historical reviews and the active backlog supplied context; their findings were not assumed to remain open without checking current code.

Evidence labels:

- **Reproduced:** a host probe invokes current production methods and demonstrates the described contract failure. The lightweight harness uses existing test filesystem/class stubs; it does not prove a physical exploit or complete applet execution.
- **Sanitizer-confirmed:** UBSan reports undefined behavior in current production source.
- **Source-confirmed:** the relevant code path lacks or contradicts the stated behavior. Its complete applet/hardware trigger was not executed during this review.
- **Acceptance gap:** implementation exists, but the required environment or end-to-end proof remains outstanding.

P1 means data corruption, isolation/recovery failure, memory safety or loss of a core runtime guarantee. P2 means a functional incompatibility, resource limitation or verification defect. There are no P0 claims. All new findings map to `RV-20261103-NN` checklists in [TODO.md](../TODO.md#functionality-review--2026-11-03); existing task owners are retained.

No firmware source, upstream CAP or hardware state was changed. Full ARM/RISC-V builds, physical flashing, cold power tests and complete API sweeps were not performed for this review. The new files under `artifacts/reviews/review_20261103/` are offline review probes and logs.

## Persistence, installation and deletion

### R02 — Persistent array replacement overwrites an older object's identity

**P1; reproduced.** [flashmemory.cpp:291](../choupi/src/jc_handlers/flashmemory.cpp#L291) derives an array body tag by appending `FFFF` to its referencing field tag. [setPersistentField_Reference:1166](../choupi/src/jc_handlers/flashmemory.cpp#L1166) uses that same derived tag for a newly assigned array. It is independent of the field's immediate alias record, but **not unique across successive objects assigned to the same field**.

Reproduction with real `Static_Handler`, `FlashMemory_Handler` and `Heap`: persist array A containing `11` in static slot 1; alias A from slot 2; assign a new array B containing `22` to slot 1. Both A and slot 2 then read `22`:

```text
ARRAY_RETARGET old=0003 new=0005 old_byte=22 alias_byte=22 expected=11/11
```

This is observable corruption during normal reference reassignment, without power loss or GC. It also compromises reachability analysis because separate objects can acquire the same persistent identity. Instance serialization also uses a first-field-derived identity and needs the equivalent replacement audit; the object variant was not reproduced here.

**Required fix:** assign durable identities per object allocation/generation; make fields point to those identities. Preserve A until its last reference is gone. Test replacement, clearing, aliases read in either order, GC, transactions and fresh-heap restore. [Probe log](../artifacts/reviews/review_20261103/array-retarget.log)

### R03 — Transaction abort does not restore cached static references

**P1; reproduced.** [Static_Handler::getPersistentRef:157](../choupi/src/jc_handlers/jc_static.cpp#L157) returns the heap's cached static root before consulting persistent storage. `setPersistentRef()` changes that root, while [Heap:583](../choupi/src/heap.cpp#L583) does not associate the cache with the transaction rollback generation. Instance fields have a rollback-generation mechanism; static roots do not.

Persist A, begin a transaction, set the static field to null, abort, and read it again. The record restores A, but the cache returns null:

```text
STATIC_ABORT begin=1 abort=1 old=0003 cached=0000 restored_record_byte=11 expected_ref=0003
```

The same stale cache participates in root enumeration, so the problem affects identity and GC safety as well as returned values.

**Required fix:** restore or invalidate cached static references on successful abort and failed commit; preserve canonical object identity when reloading. Cover null, object and array substitutions, aliases and collection immediately after abort. [Probe log](../artifacts/reviews/review_20261103/static-abort.log)

### R04 — DELETE prefix erases bypass transaction before-images

**P1; source-confirmed.** [cap_load.cpp:373](../src/cap_load.cpp#L373) deletes applet fields through raw `fs_erase_prefix()`. Package deletion calls `fs_erase_package_state()`. Their Pico implementations directly erase overlay records and compact them; see [pico_filesystem.cpp:1479](../src/pico_filesystem.cpp#L1479) and [1620](../src/pico_filesystem.cpp#L1620).

The transaction begun by `DeleteBackend::begin()` only restores records captured through `snapshot_persistent_tag()`. Raw prefix/package erasure never calls it. If a later marker write, erase or commit fails, `rollbackPersistentWriteTransaction()` cannot recreate the already-erased applet/static records. Its rollback sync can then persist those erasures despite DELETE returning an error.

`test-gp-delete` passes 26/26, but it tests the generic orchestration with a mock backend. The overlay suite tests storage erasure, not this combined VM transaction path.

**Required fix:** make namespace deletion participate in a rollback/recovery protocol at the actual storage boundary. Inject a failure after one real deletion and before publication; require all prior live values and registry entries to remain usable. A passing mock rollback is insufficient.

### R05 — DELETE and LOAD publication lack complete cross-store recovery

**P1; source-confirmed.** [deleteObject:1094](../src/cap_load.cpp#L1094) commits filesystem changes before removing the instance/package from CAP metadata. For an instance DELETE, the persistent root can therefore be durably gone while the CAP registry still lists that instance. A failed metadata write or interruption leaves an applet that lists successfully but cannot restore. Unlike INSTALL, this operation has no durable replay journal. Package DELETE has a deletion marker, but failure before final CAP removal can still strand a slot and needs an explicit completion path.

The LOAD path has the reverse ordering: [finishLoad:758](../src/cap_load.cpp#L758) publishes CAP storage before starting/committing package-enable metadata. Failure leaves a stored CAP that occupies a slot and prevents the same package AID from loading again, without a matching completed package state.

**Required fix:** define and implement recovery for each publication point, including retry semantics and cleanup of incomplete LOADs. Fault-inject between stores and after each durable transition. Successful filesystem snapshots alone do not establish atomic package lifecycle.

### R06 — INSTALL checks registry conflicts after committing applet state

**P1; source-confirmed.** [installAndMakeSelectable:803](../src/cap_load.cpp#L803) validates the CAP and imports, then allocates an owner and runs applet INSTALL. It does not first reject an already registered instance AID or a full per-package instance table. It commits object writes and an INSTALL journal at [948](../src/cap_load.cpp#L948), then discovers publication failure in `choupi_store_cap_instance()`.

[cap_store_mark_package_installed:581](../src/cap_store.cpp#L581) rejects conflicting AIDs, owners and table capacity. By then the attempted install may already have changed package statics and written an orphan object graph. A journal whose requested AID belongs to another package cannot replay and causes `recover_pending_install_journals()` to fail, blocking later installs. Same-package duplicate replay also does not verify owner equality before clearing the journal.

**Required fix:** preflight/reserve registry capacity and AID ownership before invoking INSTALL, then recheck publication invariants and recover idempotently. Test duplicates in the same/different package and a full instance table; rejected requests must leave existing state untouched and future installation usable.

### R07 — Applet transactions can escape lifecycle and reset boundaries

**P1; source-confirmed.** The transaction flag and snapshots in [flashmemory.cpp:78](../choupi/src/jc_handlers/flashmemory.cpp#L78) are runtime-global. The [APDU completion path:1655](../choupi/src/main.cpp#L1655), lifecycle invocation and [card-reset path:1022](../choupi/src/main.cpp#L1022) contain no corresponding automatic rollback. `fs_sync()` deliberately returns success without publishing while a transaction remains active.

An applet can begin a transaction, write, and return or throw without closing it. Later commands then run with its transaction still open. A PC/SC reset clears selection/transients but leaves the in-memory transaction and modified overlay intact; another applet can encounter or close the inherited transaction. A real power interruption and a warm reader reset consequently have different semantics.

Java Card RE 3.0.5 §7.6.2 requires the runtime to abort an applet-initiated transaction at these lifecycle exits; reset recovery is covered by §7.5. [Oracle RE specification](https://docs.oracle.com/cd/E59935_01/JCCRE.pdf)

**Required fix:** add a lifecycle transaction guard that distinguishes runtime-internal INSTALL transactions from applet transactions. Validate normal return, uncaught exception, timeout, rejected selection, deselection and warm reset, followed by an unrelated applet command.

## Ownership, contexts and object lifetime

### R08 — GC drops reference owner tags in volatile Object arrays

**P1; reproduced.** [JC_Array::setReferenceEntry:655](../choupi/src/jc_types/jc_array.cpp#L655) now permits foreign references in volatile wildcard arrays and records their owner. However, [Heap::visitChildReferences:723](../choupi/src/heap.cpp#L723) visits only the compact handle and discards its owner. `Context::visitRootReferences()` scans global-array roots, but does not discover foreign roots retained in another package's ordinary arrays.

A two-context probe creates equal compact handles `0003`. B retains A's array in a B-owned Object array. B's GC marks its unrelated colliding array, while A's GC reclaims the object that B retained:

```text
FOREIGN compact=0003 collision=0003 owner=20; target_gc reachable=2 reclaimed=0 complete=1; owner_gc reclaimed=1 complete=1
```

Both walks report complete. Reuse of the reclaimed owner slot can make a retained opaque reference denote a different later allocation.

**Required fix:** carry owner provenance through graph edges and route foreign roots to the owning package, or disable this newly allowed retention until that is safe. Include owner slot reuse, package deletion and non-colliding handles. [Probe log](../artifacts/reviews/review_20261103/foreign-array-gc.log)

### R09 — Object sensitive results have no owner provenance

**P2; reproduced at the native state boundary.** [Context:43](../choupi/src/context.cpp#L43) stores result state globally across contexts, but its object value is only `jref_t`. [assertSensitiveResultObject:782](../choupi/src/context.cpp#L782) compares compact handles; [root enumeration:885](../choupi/src/context.cpp#L885) submits that same handle into every participating context's heap.

Setting an A-owned result then asserting a different B-owned object with the same compact handle succeeds. B also retains its wrong object as a root:

```text
SENSITIVE left=0003 right=0003 cross_owner_assert_accepted=1 wrong_heap_arrays_retained=1
```

This probe checks the real Context API. The exercised AID result producers normally return global objects, so it does **not** demonstrate that current `getAID()` calls are exploitable through this collision.

**Required fix:** store owner plus handle, normalize global references, compare full identity and root only in the owning heap. Add an interpreted SIO producer/assertion test with distinct owners and equal compact values. [Probe log](../artifacts/reviews/review_20261103/sensitive-owner.log)

### R12 — Reset does not clear CLEAR_ON_DESELECT arrays

**P1; reproduced.** [Heap::clearTransientArrays:454](../choupi/src/heap.cpp#L454) matches the requested event exactly. The card-reset path calls it with `CLEAR_ON_RESET` and does not separately clear deselect arrays. The reset operation therefore leaves `CLEAR_ON_DESELECT` data intact:

```text
RESET clear_on_reset=00 clear_on_deselect=22 expected=00/00
```

The JCSystem 3.0.5 contract includes reset among the clearing events for deselect arrays. [Oracle JCSystem API](https://docs.oracle.com/cd/E59935_01/api/javacard/framework/JCSystem.html)

A sequence that selects another applet before reset can accidentally hide this defect by clearing the array earlier. Existing physical transient results must be checked for that sequencing distinction.

**Required fix:** reset must clear both classes across active and inactive contexts without invoking applet `deselect()` as a reset callback. Test reset directly from the active applet, inactive package contexts and transient-key flags. [Probe log](../artifacts/reviews/review_20261103/reset-clearing.log)

### R13 — Restored transient arrays have the wrong length and uninitialized storage

**P2; reproduced length error, source-confirmed initialization error.** The tagged constructor at [jc_array.cpp:106](../choupi/src/jc_types/jc_array.cpp#L106) allocates `tag length + 1 + element bytes`. [size():238](../choupi/src/jc_types/jc_array.cpp#L238) divides the entire backing length for a transient array instead of excluding the tag prefix. A restored byte array of length four with a three-byte tag reports eight elements.

The constructor uses `new uint8_t[...]` without initialization and writes only the tag prefix. The logical transient contents are not explicitly initialized to Java defaults. This is a potential stale-memory disclosure; its physical contents were not measured in this review. The inflated length can also allow a nominally valid access that later fails against backing storage.

**Required fix:** represent logical length separately or calculate it correctly; initialize only the data region and preserve its tag metadata. Validate byte/short/int/reference arrays after fresh restore and after clear/reset, including the largest accepted sizes. [Probe log](../artifacts/reviews/review_20261103/restored-transient-size.log)

### R21 — Cross-context SIO calls replace server exceptions with SecurityException

**P2; source-confirmed.** After the server interpreter returns, [bc_invoke.cpp:1076](../choupi/src/jc_bytecodes/bc_invoke.cpp#L1076) turns every non-`9000` status into `Exceptions::SecurityException`. It does not propagate the server's exception type, reason or reference to the client.

The current fixture throws SecurityException, so its passing exception test cannot detect this substitution. A service throwing `CryptoException`, a different runtime exception, or an application exception will not reach the client's matching catch handler with its original semantics.

**Required fix:** distinguish a transport/firewall denial from a Java exception crossing the SIO boundary. Implement owner-safe exception propagation and caller context restoration, including subclass identity and reason. Test at least two exception classes with distinct catch blocks and a successful follow-up call.

### R22 — Class-to-interface casts do not search superclasses

**P2; source-confirmed.** In [Class_Handler::docheckcast:155](../choupi/src/jc_handlers/jc_class.cpp#L155), class-to-interface casting inspects only the concrete class's interface list. It returns false immediately for `interface_count == 0`, and returns false after exhausting that list without traversing `super_class_ref`.

An object of `Child extends Parent`, where Parent supplies interface I, should remain an I. This path can reject casts, `instanceof`, typed array stores and Shareable compatibility checks. Some converted CAP layouts may repeat inherited interfaces and hide the issue; the conversion-independent runtime behavior is not established by that workaround.

**Required fix:** walk the class hierarchy with bounded cycle detection and correct package resolution; retain recursive superinterface handling. Validate same-package and imported superclass cases. This finding is source-based; no new CAP was produced to exercise it.

## Interpreter and execution guarantees

### R10 — The applet timeout is renewable through native and nested calls

**P1; source-confirmed.** [Interpretor::run:380](../choupi/src/interpretor.cpp#L380) records a start time, but the timeout compares against the global `applet_execution_progress_us`. [choupi_vm_native_progress:48](../choupi/src/interpretor.cpp#L48) replaces that value on native progress. A nested interpreter also resets the same global when entering SIO/lifecycle work.

An applet looping through native operations that report progress, or repeatedly entering nested calls, can keep renewing its apparent budget. The 120-second guard is therefore an inactivity timer in these paths, despite comments describing a bound on the complete applet operation. One long native call also cannot be interrupted by a check that runs only between bytecodes.

**Required fix:** separate an immutable top-level deadline from watchdog/progress timestamps; share that deadline across nested calls and enforce it in interruptible native loops. Use an injectable clock to test native progress, repeated SIO, nesting and timeout unwind without waiting minutes. Preserve successful long RSA behavior within the chosen policy.

### R18 — Large int-array allocation silently wraps its byte length

**P2; reproduced.** [JC_Array constructor:57](../choupi/src/jc_types/jc_array.cpp#L57) multiplies element count by width and passes the result into `JCVMArray`, whose length is `uint16_t`. A request for 16,384 ints becomes 65,536 bytes, then truncates to zero:

```text
INT_ARRAY requested=16384 actual=0
```

Other sizes above that boundary can produce smaller arrays rather than a clean resource exception. Serialization also stores aggregate sizes in 16-bit temporaries and needs the corresponding width audit.

**Required fix:** use checked wide arithmetic before allocation/serialization. Either support the logical length or reject it with the documented Java Card resource error before returning an object. Test boundaries around 16,383/16,384 ints and record/header limits for all primitive types. [Probe log](../artifacts/reviews/review_20261103/int-array-size.log)

### R19 — Minimum-value division returns zero

**P2; reproduced.** The special overflow cases in [bc_idiv:255](../choupi/src/jc_bytecodes/bc_arithmetic.cpp#L255) and [bc_sdiv:1025](../choupi/src/jc_bytecodes/bc_arithmetic.cpp#L1025) push zero when the dividend is the minimum signed value and the divisor is -1. The bytecodes' own documented contract requires the unchanged minimum value.

```text
SDIV actual=0 expected=-32768
IDIV actual=0 expected=-2147483648
```

The neighboring remainder special case correctly returns zero and should remain distinct.

**Required fix:** return the minimum dividend for division and add short/int edge vectors for sign combinations, remainder and division by zero. Test actual bytecode execution on both compiler targets after the change. [Probe log](../artifacts/reviews/review_20261103/division.log)

### R20 — Arithmetic and word reconstruction use undefined C++ operations

**P2; sanitizer-confirmed.** `bc_iushr` and `bc_sushr` implement Java's explanatory `(2 << ~s)` expression directly in C++, where `~s` is negative. The Java expression's masked-shift rules do not apply to C++. UBSan reports negative shift exponents at [796](../choupi/src/jc_bytecodes/bc_arithmetic.cpp#L796) and [1522](../choupi/src/jc_bytecodes/bc_arithmetic.cpp#L1522), even for zero shifted by zero.

`bc_iadd` also executes signed overflow before casting. UBSan reports `2147483647 + 1`, plus a negative left shift while [Stack::pop_Int:341](../choupi/src/stack.cpp#L341) reconstructs a word through `SHORTS_TO_INT`. Related subtraction, multiplication, negation, increment and signed left-shift paths need the same audit.

The unsanitized zero-shift and overflow probes happen to return expected values on this host. That is not portable correctness under optimization.

**Required fix:** implement wrapping operations and reconstruction in unsigned fixed-width types with explicit signed interpretation. Respect Java Card short-shift semantics, which use sign extension to 32 bits; do not blindly substitute a 16-bit logical shift. [UBSan shift log](../artifacts/reviews/review_20261103/ubsan-unsigned-shift.log), [overflow log](../artifacts/reviews/review_20261103/ubsan-overflow.log)

### R28 — Uploaded CAP execution does not have a complete trust boundary

**P1; source-confirmed, no on-device malformed program executed.** Three protections remain incomplete:

1. **Instruction and method bounds.** [pc_t.hpp:82](../choupi/src/jcvm_types/pc_t.hpp#L82) fetches directly through a raw pointer; relative branches have no containing-method bound. [Method_Handler::callMethod:88](../choupi/src/jc_handlers/jc_method.cpp#L88) reads complete method headers after `getMethodFromOffset()` has checked only the first byte. The Method payload validator checks exception-table length, not instruction boundaries, method bodies or branch targets. Truncated methods or out-of-range branches can therefore reach unchecked reads.
2. **Native opcode origin.** [bc_impdep1:81](../choupi/src/jc_bytecodes/bc_others.cpp#L81) forwards an applet-supplied short to generated native dispatch without requiring execution in trusted ROM. The generated switch includes internal result-state and APDU setters. No uploaded-code verifier shown here rejects that opcode. This demonstrates a missing origin boundary, not arbitrary native memory access.
3. **Heap field kinds.** `JCVM_TYPED_HEAP` is disabled in [jc_config.h](../choupi/src/jc_config.h). [getField_Reference:385](../choupi/src/jc_types/jc_instance.cpp#L385) reinterprets a field word without checking its type; primitive setters can overwrite its kind. A malformed sequence can move numeric field contents back onto the stack as a reference, bypassing the newer typed operand protections.

The passing 100,000-input parser fuzz test exercises serialized parsing, not hostile instruction execution. Authenticated loading limits who supplies the program; it does not validate the program.

**Required fix:** define the uploaded-CAP trust model explicitly; enforce execution bounds and privileged-opcode origin regardless of parser success, and add verification or dynamic field-kind/access checks. Test malformed instructions and nested linkage under sanitizers, then controlled physical failure/recovery. Keep valid upstream CAPs unchanged.

## Crypto and framework API behavior

### R11 — Cipher copies outlive transient-key clear events

**P1; source-confirmed.** [initializeSymmetricCipher:492](../choupi/src/native_cipher.cpp#L492) validates the original key once, then copies its bytes into an ordinary array held by the Cipher object. `updateSymmetric()` and `doFinalSymmetric()` check only `CIPHER_INITIALIZED`; they do not recheck the source key. [initializeRsaCipher:416](../choupi/src/native_rsa_cipher.cpp#L416) similarly copies modulus/private components into ordinary Cipher arrays.

Clearing a transient source key on deselect/reset does not clear these copies or invalidate the Cipher. If the Cipher is retained persistently, its ordinary key-copy arrays can also be serialized. Fixing R12 alone will not fix this independent lifetime problem. The Java Card 3.0.5 Cipher API ties validity to the source transient key's clear event. [Oracle Cipher contract](https://docs.oracle.com/cd/E59935_01/api/javacardx/crypto/Cipher.html)

**Required fix:** retain checked key identity and appropriate lifetime metadata, or use workspace that clears with the key. Test retained Cipher objects across deselect, reader reset and fresh restore for symmetric and RSA transient keys. Modification of a key after `init()` is separately unspecified; this finding concerns defined lifecycle clear events.

### R14 — Signature workspace allocation selects the wrong overload

**P2; reproduced at the exact production allocation expression.** [createSignature:669](../choupi/src/native_signature.cpp#L669) allocates IV, message and recovery arrays using `heap.addArray(length, JAVA_ARRAY_T_BYTE, ClearEvent::CLEAR_ON_RESET)`. [appendBytes:334](../choupi/src/native_signature.cpp#L334) does the same on expansion.

There is no `Heap::addArray(..., ClearEvent)` overload. The enum binds to the third parameter of the reference-component-type overload. The resulting byte array is **not transient**, and its clear event is `None`:

```text
SIGNATURE_ARRAY is_transient=0 clear_event=255 expected=1/1
```

Thus message/recovery workspace can survive reset and, when reachable through a persistent Signature object, become persistent storage traffic. This also helps explain why long workloads should inspect native-object persistence, rather than attributing every storage increase to applet data.

**Required fix:** construct transient arrays explicitly and make the API type-safe so the enum cannot silently bind as a component token. Verify both initial and expanded buffers. [Probe log](../artifacts/reviews/review_20261103/signature-array-overload.log)

### R15 — Crypto session metadata is not reset or excluded from transactions

**P2; source-confirmed.** [MessageDigest:91](../choupi/src/native_message_digest.cpp#L91) stores its buffered count in an ordinary instance field while its bytes use a reset-cleared array. The runtime reset clears arrays but does not zero this count. A retained digest after warm reset can therefore hash cleared bytes from an old count instead of starting empty.

Cipher initialization/mode/buffering and Signature message/recovery counters are also ordinary fields. There is no native-object lifecycle reset hook covering them. When such objects are persistent, intermediate writes go through normal persistent setters and can enter the active transaction journal. This conflates object persistence with cryptographic session state.

The 3.0.5 digest API requires reset to restore construction state and excludes intermediate state from transactions. [Oracle MessageDigest contract](https://docs.oracle.com/cd/E59935_01/api/javacard/security/MessageDigest.html)

**Required fix:** define native engine session state separately from persistent Java object identity. Test update → warm reset → final, update inside an aborted transaction, retained objects after cold restore and Signature recovery state. Fixing buffer allocation alone is insufficient.

### R16 — CBC doFinal restores the supplied IV instead of zero

**P2; source-confirmed.** [restoreInitialIv:473](../choupi/src/native_cipher.cpp#L473) copies `CIPHER_INITIALIV` back into the current IV after successful `doFinal()`. An explicit nonzero initialization IV is reused for the next operation. The 3.0.5 contract resets CBC IVs to zero after completion. [Oracle Cipher.doFinal](https://docs.oracle.com/cd/E59935_01/api/javacardx/crypto/Cipher.html#doFinal-byte:A-short-short-byte:A-short-)

A one-shot known-answer vector with a nonzero IV cannot catch this; the first operation is correct. The failure needs two completions without reinitialization.

**Required fix:** implement the selected API version's algorithm-specific post-final state. Compare the second AES/DES CBC result to a newly initialized zero-IV engine, then verify that an explicit new `init()` restores the supplied IV. Keep CTR policy separate.

### R17 — MessageDigest update is limited to 2,046 total bytes

**P2; source-confirmed limitation.** [native_message_digest.cpp:29](../choupi/src/native_message_digest.cpp#L29) allocates a fixed 2,046-byte input buffer. `update()` appends the whole message; reaching the cumulative limit throws `ILLEGAL_USE`, even with small valid chunks and available memory.

This is not streaming digest state. A legal sequence of three 1,024-byte updates fails on its second update, long before Java Card short-array or hash input-size limits. The selected digest can pass support detection and ordinary short KATs while failing a common application workload. The profile does not disclose this cumulative limit.

**Required fix:** use native incremental digest contexts with correct reset/transaction lifetime, or explicitly narrow the declared compatibility contract until implemented. Test more than 2,046 cumulative bytes across APDUs and block boundaries, including empty final input and reuse after completion.

### R23 — Non-atomic Util methods do not prevalidate their ranges

**P2; source-confirmed.** The active SDK [Util.arrayCopyNonAtomic:204](../choupi/javacard-sdk/javacard-api/src/javacard/framework/Util.java#L204) and [arrayFillNonAtomic:365](../choupi/javacard-sdk/javacard-api/src/javacard/framework/Util.java#L365) enter loops without validating all null, negative and out-of-bounds arguments first.

Negative lengths skip the loop and return a computed result; null buffers with zero length can avoid any dereference. For an overlong range, valid prefix bytes may already have changed before a bytecode bounds check throws. The documented API rejects those arguments before copying/filling. [Oracle Util API](https://docs.oracle.com/cd/E59935_01/api/javacard/framework/Util.html)

These are existing active framework bodies, not proposed Java provider work. New behavior must follow the repository's native implementation boundary.

**Required fix:** enforce complete validation in native API dispatch before mutation, with tests for negative/zero lengths, nulls, boundary offsets and invalid overlapping ranges. Verify exception type, destination contents and SensitiveResult after failure.

### R24 — Non-atomic persistent updates still enter the transaction journal

**P2; source-confirmed.** Those Util loops use ordinary array stores. [setPersistentField_Array_Byte:1729](../choupi/src/jc_handlers/flashmemory.cpp#L1729) unconditionally snapshots a persistent record whenever a transaction is active. The generic atomic and non-atomic native helpers also share the same write path. There is no non-atomic mutation scope or accounting bypass.

Consequently a large non-atomic copy/fill inside a transaction can consume commit capacity, throw `BUFFER_FULL` and participate in rollback. Non-atomic methods expressly bypass transaction participation and commit-capacity limits. The difference matters even when final copied bytes are correct. [Oracle Util contract](https://docs.oracle.com/cd/E59935_01/api/javacard/framework/Util.html)

**Required fix:** provide a native mutation path with the selected non-atomic semantics, including interaction with records already journaled by atomic writes. Test mixed atomic/non-atomic writes and abort on the same and different persistent arrays, including a record larger than commit capacity. Do not weaken ordinary transaction accounting globally.

## USB, card routing and host regression coverage

### R01 — CCID length overflow can escape the receive-buffer limit

**P1; source-confirmed.** At [ccid_device.cpp:1075](../src/ccid_device.cpp#L1075), a 32-bit USB `dwLength` is checked as `payload_length + 10 > kMaxCcidMessage`. Addition occurs in 32-bit unsigned arithmetic before comparison. Values `FFFFFFF6` through `FFFFFFFF` wrap to expected total lengths 0–9 and pass the check.

For `FFFFFFF6`, `rx_expected` remains zero. Repeated full packets can advance `rx_length` to the 320-byte array boundary, where [queue_out:304](../src/ccid_device.cpp#L304) arms another 64-byte receive at `rx_buffer + rx_length` **before** the completion callback checks the resulting length. For other wrapped values, processing can begin with fewer than the required ten header bytes and `rx_expected - 10` underflows.

**Required fix:** compare `payload_length` to `max_total - header_size` before adding; validate minimum header/slot/state and exact frame length; never arm an endpoint beyond remaining capacity. Exercise all wrap values and packet fragmentation in a host shim of the production driver. No malformed USB command was sent to hardware.

### R25 — Physical card-management and applet routing have different contracts

**P2; source-confirmed.** Three differences appear in [process_message:444](../src/ccid_device.cpp#L444):

- Authenticated GP handling and its `6982` rejection branch are followed by a separate SELECT/applet-dispatch chain. An ordinary command can therefore be processed by the card manager and then by an active applet, which can replace its response. The routes are not mutually exclusive.
- Only the empty-AID ISD SELECT gets the built-in FCI at [775](../src/ccid_device.cpp#L775). Selecting the ISD's advertised AID explicitly goes through the applet registry and normally returns `6A82`. VPCD supports both forms.
- `XfrBlock` does not require an active slot or validate a nonzero requested slot, despite power/slot state being tracked. Power-off state does not enforce the same dispatch gate as VPCD.

These differences weaken the emulator as an oracle for physical routing and make outcomes depend on selection/session history.

**Required fix:** define one card-session dispatch contract with exactly one route per command, explicit ISD identity and activation/slot checks. Test GP commands while an applet is selected, failed authentication, explicit/default ISD selection and APDUs while powered off. Cover the production CCID path, not just helper encoders.

### R26 — Failed final CCID submission can leave the reader unarmed

**P2; source-confirmed.** [send_response:363](../src/ccid_device.cpp#L363) clears receive state, waits at most 100 ms for an outstanding time extension, and tries final submission. If an extension remains in flight or submission fails, it only increments a counter and clears the ZLP flag.

Bulk OUT is normally rearmed after a successful final IN completion. A later extension completion deliberately returns without rearming it. Therefore this failure path can produce neither a final response nor a new OUT receive, leaving a reader that requires reset/re-enumeration. The 9/9 shared progress-flow tests prove the helper refuses an unsafe final submit, but not recovery in the surrounding driver.

**Required fix:** retain a pending final response for bounded retry, or transition to an explicit recoverable abort/reset state that safely rearms the endpoint. Test extension completion just after the wait bound, failed IN submission and subsequent slot-status/APDU recovery.

### R27 — VPCD session tests are stale and mask selection regressions

**P2; reproduced.** `./tools/test-vpcd-session` fails to compile: [vpcd_session_test.cpp:133](../tests/unit/vpcd_session_test.cpp#L133) still calls a two-argument constructor, but [Session:34](../choupi/src/vpcd_session.hpp#L34) now accepts only callbacks.

A review copy changed **only that constructor invocation** and ran against current `vpcd_session.cpp`: 19 checks passed, two failed. [Session:148](../choupi/src/vpcd_session.cpp#L148) always passes `true` to `clear_or_deselect()` for any AID SELECT, including a different/unknown AID. It also maps every restore failure to `6A82`, losing the tested distinction between restore failure and missing application. On the real VM path, the wrong boolean can affect `reSelectingApplet()` state.

**Required fix:** restore the test's build, track the actual selected AID and retain meaningful restore failure status. Expand to two known applets, unknown AID, same-AID reselection, rejected `select()` and corrupted restore. Do not simply change assertions to the current wrong behavior. [Original compile log](../artifacts/reviews/review_20261103/vpcd-session.log), [adapted run](../artifacts/reviews/review_20261103/session-adapted.log)

## Other inspected areas and existing acceptance work

These observations are material, but are not additional newly reproduced defects:

- **Filesystem and CAP metadata foundations:** snapshot CRC/generation checks, version migration, compaction and mirrored CAP metadata have substantial offline coverage. The overlay suite passed, including its modeled power cuts. R04–R06 concern orchestration around those primitives; they do not imply that snapshots or the INSTALL journal are absent.
- **Package deletion dependencies:** DELETE does not visibly walk other packages' import dependencies before removing a package. Add a library/client scenario under GP-01 and determine the supported deletion policy; this review did not execute that integration case.
- **Global heap growth:** user-created global arrays are retained in process-global `shared_ptr` slots. Reset clears their data but does not reclaim slots; ordinary applet GC skips globals. `makeGlobalArray()` has no explicit lifetime release path, whereas scoped RMI arrays do. Repeated use may exhaust SRAM/handles. Establish a resource/lifetime policy under CTX-01/STORE-01 before claiming long-running support.
- **Cryptographic hardening:** imported/generated RSA private operations still need the threat-model and blinding/fault-verification acceptance already tracked by HARD-01. Scratch cleanup and correct signatures do not establish those properties. This review did not measure side channels or perform fault injection.
- **Profiles and upstream test limits:** unsupported algorithms, absent optional packages, extended APDUs and logical channels remain declared scope limits. The known mislabeled RSA-3072 probes and undersized SHA-512 PSS vector are not reopened as implementation defects.
- **Release evidence:** Windows profile workflows, actual interrupted writes/reclamation, cold restoration of newer owner/alias graphs, final combined-image static performance and three complete integration passes remain acceptance gaps. None was closed by this offline review.

The largest testing weakness is coverage between layers: the parser and mock DELETE backend pass while execution and real deletion transaction paths remain unverified; local-array GC passes while a foreign retained reference fails; one-shot crypto tests pass while reset/reuse state is wrong.

## Recommended implementation order

1. Repair persistent identity and transaction visibility first: R02–R07. Root/reclaimer acceptance depends on those identities and rollback guarantees being trustworthy.
2. Close ownership and reset defects: R08, R09, R11–R15. Keep normal persistent reclamation disabled while those paths remain unresolved.
3. Harden execution and transport boundaries: R01, R10, R20, R28, then R25–R27. Restore the broken session suite early so subsequent routing changes have working regression coverage.
4. Complete API behavior and reusable crypto-state tests: R16–R19 and R21–R24, then run the current profile's full acceptance matrix on one nominated image.

Each fix should have a focused regression demonstrating the original failure, plus the repository's required build and physical gates when runtime source changes. Preserve the existing API/CAP boundary and keep image-specific evidence attached to results. Updating the backlog or passing an offline probe does not close the existing physical acceptance gates.
