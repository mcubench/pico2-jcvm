# RESOURCE-01 code review: causes of long-run persistent-storage exhaustion

Date: 2026-11-10. Reviewer: Claude Opus 5.5. Scope: static code review of the
RAM heap, persistent object serialization, both filesystem backends, and the
native crypto API paths. No code was changed, no repo tooling was run, and no
simulated or physical device was used. Line numbers refer to the working tree
at root commit `21e7d45e` (with the uncommitted changes present at that time).

Backlog task: [RESOURCE-02](../TODO.md#resource-02) (implementation of these
fixes), which feeds [RESOURCE-01](../TODO.md#resource-01).

## Verdict

The exhaustion is mostly **not** caused by creating keys, and it can't be fixed
by finishing object deletion alone. The main cause is that **ordinary crypto
calls on a stored (persistent) crypto object create new flash records on every
call.** On the RP2350 these records are never removed. Current RESOURCE-01 work
concentrates on removing unreachable objects after a deletion request, which
only drains the leak after it happens.

## C1. Main cause: every `init()` writes new persistent records

1. JCAlgTest keeps its `Cipher`/`Signature` objects in applet fields, so those
   objects are persistent.
2. `JC_Instance::setField_Reference`
   (`choupi/src/jc_types/jc_instance.cpp:822-833`) persists every reference
   written into a persistent object via `setPersistentField_Reference`.
3. For an array that is not yet persistent, `setPersistentField_Reference`
   (`choupi/src/jc_handlers/flashmemory.cpp:1520-1539`) always allocates a new
   identity, writes a new body record (`field_tag + FFFF + id`) and rewrites
   the field's alias. The previous body is left behind as an orphan.
4. The native `init` code allocates new work arrays on **every call** instead
   of reusing them:
   - **RSA `Cipher.init`** (`choupi/src/native_rsa_cipher.cpp:485-516`):
     zeroes the old arrays byte by byte (`wipeCipherArray`), then allocates new
     MODULUS, EXPONENT, KEYDATA and BUFFERED arrays. For a public key, MODULUS
     and EXPONENT are ordinary persistent arrays of key length; their bodies
     hold full key bytes, and `loadKeyComponent` fills them one byte at a time
     (one persistent write per byte).
   - **AES/DES `Cipher.init`** (`choupi/src/native_cipher.cpp:587`):
     `allocateKeyWorkspace` creates a new KEYDATA array on every call.
   - **Growing message buffers** in `native_signature.cpp:340-350`,
     `native_rsa_signature.cpp:176-187` and `native_rsa_cipher.cpp:410-415`
     also create a new body each time they grow.
5. Every allocation also rewrites the identity counter record
   (`flashmemory.cpp:404`).

Estimate: an RSA-2048 public `init` leaves about 4 new records and ~600 bytes
behind, plus 5–8 record rewrites. A performance test that repeats `init` in a
loop therefore grows storage linearly with the iteration count, without
creating any new keys. This matches the logged orphan share (1,485 of 1,691
owner records unreachable).

## C2. Transient arrays get a new body on every assignment

`writeArray` assigns a persistent tag only to non-transient arrays
(`flashmemory.cpp:859`), and the reuse branch at line 1522 requires
`!isTransientArray()`. A transient array is therefore never recognised as
already stored: each assignment into a persistent field, even of the same
array, allocates a new identity and record. This is the logged HMAC
`TYPE_HMAC_TRANSIENT_DESELECT` leak (8 records per repetition) and also covers
the transient work arrays in C1.

## C3. No orphan reclamation in production

- `requestObjectDeletion()` throws `SystemException.ILLEGAL_USE` unless
  `PICO2_TEST_OBJECT_DELETION=1` is set on PC (`choupi/src/jni.cpp:1913-1923`).
- On the Pico the persistent reclaimer is compiled only under
  `CHOUPI_DEBUG_PERSISTENT_GC` (`choupi/src/main.cpp:795`).
- Pico compaction (`compact_deleted_overlay_records`, `src/pico_filesystem.cpp`)
  only drops explicitly deleted records, never live orphans.
- RAM GC (`Heap::collectUnreachableFrom`) frees RAM handles only; it never
  erases flash bodies.

Hard limits:

| Backend | Capacity | Failure |
|---|---|---|
| RP2350 | 96 KiB payload and 8,192 records, held in RAM (`src/pico_filesystem.cpp:31,77`) | ~150 RSA-2048 public inits, or ~8k AES inits by record count, can fill it |
| PC VPCD (Rust FS) | ~176 KiB in data sectors 1, 2, 3, 6 (`choupi/os/src/arch/host/constants.rs`) | `F205`/`NO_RESOURCE` when live + orphan data exceeds capacity |

## C4. Why runs slow down, time out, and possibly reset

- **PC:** `edit_at` rewrites the whole record for each byte written
  (`choupi/os/src/fs/mod.rs:1236-1251`). Zeroing and refilling a 256-byte
  modulus byte by byte is ~512 full-record appends, ~140 KB of log per RSA
  init — close to one 128 KiB compaction per init. This matches the 55–102 s
  APDUs and the 120 s watchdog hits. Near capacity, each compaction recovers
  less, so compactions become more frequent. The file index uses a fixed 32
  buckets (`fs/mod.rs:234`), so lookups also slow as records accumulate.
- **Pico:** every write moves the record to the end of the overlay (`memmove`
  of up to 96 KiB plus a loop over all 8,192 index entries, `append_overlay`).
  After each APDU that dirtied the overlay, `fs_sync`
  (`src/ccid_device.cpp:998,1025`) erases and reprograms the whole snapshot
  (up to ~160 KiB) inside `flash_safe_execute(..., 5000)`
  (`src/pico_filesystem.cpp:385`). Sync time grows with orphan bytes, and the
  two slots wear with every APDU.
  - **Hypothesis (unverified):** growing sync time and USB going unserviced
    during flash operations could explain the physical reader disappearance
    (JC-RESET-01). Measure `persist_overlay` duration against
    `overlay_bytes_used`.
- **RAM handle tables** are `std::list` with linear `at()`
  (`choupi/src/jcvm_types/list.hpp`) and never shrink, so `getArray`,
  `getInstance` and `getPersistentReference` slow down over a run. This costs
  CPU time; it does not exhaust memory.

## C5. Correctness bugs behind the current saved-state replay failure

The latest handoff chases APDU 410 returning `6F00` because array tag
`...FFFF00000005` is missing. Likely causes:

- **Persistent arrays are not repaired after transaction rollback.** Rollback
  erases bodies created in the transaction. Instances detect a missing body and
  re-persist (`flashmemory.cpp:1710-1733`); `JC_Array` has no such check and
  no rollback-generation tracking, so the RAM array keeps a tag to an erased
  body. Reads/writes then throw `IOException`, and line 1526 writes an alias
  to the missing body.
- **The identity counter appears to have gone backwards.** Splitting the
  failing tag: `03013894 | FFFE…42 | 0303 | FFFE…47 | 0606 | FFFE…01 | 0000 |
  FFFE…02 | 0909 | FFFF…05`. Objects with identities 1, 2 and 5 sit *under*
  objects 0x42 and 0x47. The code always assigns a parent's identity before its
  children and the counter is monotonic, so this requires a counter reset. The
  counter is cached in a process-local `static` (`flashmemory.cpp:370`) while
  its flash record is subject to transaction rollback; if the first counter
  record is created inside an aborted transaction it is erased, and a restart
  then begins again at 1. Reused identities can place a new body on an old
  body's tag, so a dangling alias could resolve to an unrelated object.
- **`computeTag` writes the low byte twice** (`flashmemory.cpp:891-892`).
  Element indices `i` and `i+256` produce the same tag, and index 255 produces
  `FFFF`, the array-body marker. That collision can mislead the tag-prefix
  reachability check and prefix erases.

## Other observations (lower priority)

- Under `JCVM_SECURE_HEAP_ACCESS`, every persistent element access builds a
  temporary `JC_Array` (`flashmemory.cpp:2064-2192`). Together with per-write
  temporary buffers this causes heavy malloc churn; long-run fragmentation is
  plausible but unmeasured.
- `setPersistentField_Array_Byte` maps any `fs_write_1b_at` failure to
  `IOException` rather than `NO_RESOURCE`, so storage exhaustion during element
  writes appears as `6F00` instead of `F205`.

## Recommended fixes (ordered)

1. **Stop the leak at the source (C1).** Give native crypto objects fixed-size
   work buffers allocated once (or kept in native RAM session state) and
   overwrite them in place on `init`. Never re-point a field of a persistent
   object on each call. For RSA, do not store public modulus/exponent copies in
   persistent arrays; read from the key or keep them in RAM.
2. **Reuse transient array bodies (C2).** Tag transient arrays when first
   stored, and skip rewriting a reference that has not changed.
3. **Write in bulk (C4).** Replace per-byte wipe and `loadKeyComponent` loops
   with single bulk record writes; stop rewriting the counter on every
   allocation (e.g. reserve identity ranges).
4. **Fix the array rollback path and identity safety (C5).** Give arrays the
   same missing-body recovery and rollback-generation handling as instances;
   make the identity counter rollback-safe and never reuse identities; fix
   `computeTag` to encode the high byte.
5. **Then** finish deferred deletion (C3) so long-term key turnover is bounded.

## Cheap confirmation experiment

Run a fixed number of `Cipher.init` calls on one stored RSA or AES cipher,
creating no new keys, and sample persistent inventory record count/bytes.
Before fix 1 the counts should grow linearly with the call count; after fix 1
they should stay flat.
