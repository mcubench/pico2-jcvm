# Pico 2 Java Card VM — CTO progress update

**Review window: 4 November 2026, 05:15 UTC–6 November 2026, 05:15 UTC.** Compared with the [3 November CTO review](CTO_IMPLEMENTATION_REVIEW.md). Evidence comes from dated entries in [progress.md](../progress.md); this is a documentation review, with no new firmware testing. Repeated records are treated as one result, and later diagnoses supersede earlier failures.

## Page 1 of 2 — What changed

**The project has made material progress in runtime correctness, cross-applet behavior and host usability. Its status remains an experimental platform under consolidation.** The strongest new evidence is physical cross-package execution and garbage-collection behavior, alongside much broader rejection of malformed applets in the emulator. The records do not establish acceptance of the latest combined firmware or production readiness. The previous review's completed 466-call Crypto emulator sweep remains historical evidence; no replacement full sweep is recorded in this window.

**Cross-applet interoperability now has stronger physical evidence.** A signed branch-offset defect caused backward branches to become large positive offsets on 32-bit ARM, aborting Shareable Interface Object (SIO) callbacks. Correcting it enabled the complete physical cross-AID regression on board `D92E743D5F640C0F`: service calls, firewall checks, exception propagation, stale proxies after reset/DELETE/reinstall, fresh lookup and cleanup. Standard GPPro's omission of optional Descriptor metadata initially blocked installation; structural CAP-derived method bounds subsequently enabled the Descriptor-free path. That initial installation failure is therefore resolved, although exact method-start verification without Descriptor remains incomplete.

The subsequent change enabled foreign references in applet-owned volatile `Object[]` arrays, with owner-aware GC roots. Physical tests demonstrate that a retained foreign byte array remains readable after caller roots are dropped and GC runs. This supersedes the earlier blanket rejection of that storage case. Persistence deliberately records a null marker for the foreign-containing array; emulator process restart verifies the field restores as null. Physical warm reset passed, but physical cold-power restoration of this behavior was not measured. Static/instance foreign-object stores and persistent arrays remain restricted.

**Runtime hardening moved from policy to demonstrated rejection.** Uploaded CAPs can no longer enter native dispatch through reserved bytecodes. New checks cover method and operand bounds, branch instruction boundaries, constant-pool imports/member targets, field kinds and exception-handler destinations/ranges. Malformed emulator cases return controlled errors while preserving card-manager access. One handler fixture previously resumed inside an instruction operand and returned success; it now fails with `6F00` and recovers.

The work also corrected an extended method header from five bytes to four. The deployed Java Card 3.0.5 corpus now scans **978 methods and 8,720 branch targets with zero clamps, out-of-range targets or misalignment**. Earlier reports of three upstream overlong methods were caused by the scanner's incorrect header assumption. A real upstream Crypto API method requiring an extended header now executes its AES known-answer test in the emulator. Focused decoder tests include **100,000 malformed inputs under ASan/UBSan**; this is not full-runtime sanitizer or physical hostile-CAP acceptance.

**Crypto and core API semantics became more consistent.** Fixes address retained Cipher/transient-key lifetime, reset clearing, restored transient-array capacity, Signature workspaces, native crypto session state and CBC reuse after `doFinal()`. The Cipher lifecycle emulator suite passes **29/29**. Arithmetic overflow/shifts, array allocation sizing, inherited interfaces, cross-SIO exception identity and non-atomic array transaction behavior also received fixes. These strengthen existing functionality; they do not establish broad new algorithm coverage. `makeGlobalArray()` now publishes its security-related object result across SIO; remaining result producers still require coverage.

**Host operation improved.** Normal startup no longer waits up to 30 seconds for a serial console or adds a 500 ms sleep. Physical boot and GPPro APDUs passed; near-instant Windows visibility is user-reported, without measured reconnect timings. CCID dispatch/GET RESPONSE routing and retention of final responses after failed time extensions were corrected, with normal-path physical checks. Emulator orphan cleanup and timeout process cleanup removed major test impediments; startup speedup was not measured. Repeatable empty-card ARM packages and clearer startup/build provenance improve delivery.

## Page 2 of 2 — What still matters most

**The remaining risk is proving the combined system across ownership, lifecycle and interrupted persistence.** Many focused fixes passed, but they span different images, profiles and backends. The latest cross-AID emulator suite passes **34/34** with a rebuilt `symm_crypto` VM. Its preceding AES-MAC failure was a profile mismatch: `current` correctly reports that algorithm unsupported. ARM/RISC-V build success and an existing board's runtime heartbeat do not prove the latest source changes on hardware.

| Priority | Important missing outcome | Evidence needed to close it |
| --- | --- | --- |
| 1 — Durable recovery and capacity | Physical cross-store interruption/retry, persistent reclamation safety, bounded repeated-use capacity and current-image cold restoration remain open. | Controlled power removal/cuts during installation, writes and reclamation; preserve live objects and unrelated owners; repeat install/run/delete with storage telemetry. |
| 1 — Complete ownership and lifecycle semantics | Package firewall context versus instance ownership remains unfinished. Foreign-reference support is selective; remaining `SensitiveResult` producers and object-result rooting need coverage. | Cross-package GC/lifecycle tests, equal-handle collisions, reset/DELETE/reinstall and physical cold restoration. Complete PIN, random, checksum, AEAD and key result-state paths. |
| 1 — Accepted release candidate | No complete current-image acceptance campaign replaces the historical broad sweeps. Cipher/transient reset hardware acceptance remains incomplete. | Freeze source/profile/image hashes; run full API/support/performance workflows and comparisons, clean up successfully, then complete three consecutive integration passes including physical power removal. |
| 2 — Host reliability | Windows no-console reconnect timing and diagnostic timeout behavior remain unmeasured; guest USB visibility does not guarantee usable PC/SC access. | At least three timed Windows reconnects, diagnostic deadline without DTR, and bounded successful APDUs on identified readers. |
| 2 — Hardening and upgrades | Descriptor-free exact method starts, exception-table framing, full-runtime sanitizer recovery and physical hostile-CAP recovery remain open. Package-cascade proxy invalidation and late-DELETE cleanup are review risks requiring reproduction. | Targeted negative/recovery tests and changed-version CAP replacement across restart/hardware; retain fail-closed behavior where proof is absent. |

Two limits should remain explicit in product claims. MessageDigest still has a documented cumulative-input limit; true streaming behavior is unfinished. Broader private-key protections and hardware-enforced isolation are not established by these software checks. Neither the two-architecture build gate nor the larger capability profile implies security certification or equivalent RISC-V runtime acceptance.

Physical access remains an execution dependency. Three runtime boards were recently USB-visible, but PC/SC registration and bounded APDU access were intermittent; a later GPPro listing timed out. Successful earlier physical tests remain valid for their recorded images, while these access failures limit subsequent validation. The records do not identify them as proof of firmware failure.

**Recommended next investment:** nominate one candidate image and evidence manifest, finish the coupled ownership/storage recovery tests, then execute release acceptance without intervening feature changes. Prioritize reproducibility and closed acceptance gates over adding algorithms. The last 48 hours materially strengthen the platform's correctness evidence; they do not yet close the reliability and security gaps identified in the previous review.
