## Findings

### R01 — P1: opcode-fetch failure escapes the interpreter's exception boundary

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** In [interpretor.cpp](../choupi/src/interpretor.cpp), `Interpretor::run()` is `noexcept`. Inside its execution loop, `stack.getPC().getNextByte()` executes **before** the `try` that wraps decode/execute. [pc_t.hpp](../choupi/src/jcvm_types/pc_t.hpp) deliberately throws `SecurityException` when a read reaches the method end.

A method that executes its last non-returning instruction and falls through therefore encounters an uncaught C++ exception at the next opcode fetch. `noexcept` turns this into termination, rather than a controlled APDU failure and manager recovery. The bounds helper correctly rejecting the read does not make this call site safe. The control-flow scanner checks instruction widths and branch targets; it does not establish that every reachable path returns or throws.

**Needed:** contain fetch, frame access, decode, execution and related diagnostics within a non-escaping recovery boundary. This was implemented in `a5a400c4`. The 2026-11-11 PC VPCD suite now covers fall-through, truncated operands, and malformed zero-length Descriptor body metadata; all three variants return bounded responses, reselect the manager, and successfully execute GET DATA (`9000`). Remaining acceptance: physical board recovery and any caller-root state not represented by the top-level APDU recovery sequence. Existing `pc_t` sanitizer tests alone cannot close this. Related owner: HARD-01 / RV-20261103-28.

### R02 — P1: nested failure cleanup removes callers instead of callees

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** [stack.cpp](../choupi/src/stack.cpp) adds frames with `emplace_front()` and normal returns remove `pop_front()`. [stack.hpp](../choupi/src/stack.hpp), `unwindToDepth()`, removes `pop_back()`. Numerous error paths in `Interpretor::run()` use this helper with a nonzero `entryFrameDepth`.

For a list `[failed nested callee, original caller]`, unwinding from two frames to one retains the failed callee and destroys the caller. A nested callback failure can then resume with the wrong locals/PC, lose roots, or encounter further errors. Top-level depth-zero cleanup empties the list and conceals the problem.

**Needed:** preserve the original caller frames and remove the newly entered frames in stack order. Validate two- and three-level calls with caught Java errors, ISO status exceptions, allocation failure and timeout. Compare retained PCs/locals/roots, not just frame count; check a successful following call. Related owner: CTX-01 / HARD-01.

### R03 — P1: local metadata is indexed before the local-variable bounds check

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** `Stack::readLocal_Short`, `readLocal_Int`, `readLocal_ReferenceValue` and `readLocal_ReturnAddress` in [stack.cpp](../choupi/src/stack.cpp) call `getValueKind(fp + local_number)` before `Frame::readLocal_Value()` checks that the local lies below `op`. The packed metadata accessor in [stack.hpp](../choupi/src/stack.hpp) does not check its index against `JCVM_STACK_SIZE`.

An uploaded instruction with a large local index in a nested frame can thus read beyond the metadata array before the later frame-local guard runs. Two-word locals additionally form/check the second word before validating the complete range. Some frame allocation checks also form candidate pointers before establishing that the offset fits the stack array. These are C++ memory/pointer-safety issues, not merely an incorrect Java exception choice.

**Needed:** validate integer offsets, local width and physical stack bounds before forming/indexing pointers or metadata; avoid partial writes for a two-word local crossing the frame end. Exercise local indices 254/255 at different frame bases under full Stack ASan/UBSan. The existing method-PC sanitizer tests do not cover this storage. Related owner: HARD-01.

### R04 — P1: OwnerPIN validation and retry state use ordinary persistent fields

**Source-confirmed contract mismatch.** The current [OwnerPIN ROM API source](../choupi/javacard-sdk/javacard-api/src/javacard/framework/OwnerPIN.java) stores `flag` and `triesLeft` in ordinary fields. `checkPIN()` decrements the counter and changes the flag through ordinary field stores; `reset()` and `resetAndUnblock()` do the same. Its own documentation says the validation flag resets on card reset and the retry/validation changes must not participate in an applet transaction.

The production field path in [jc_instance.cpp](../choupi/src/jc_types/jc_instance.cpp) journals persistent byte fields without PIN-specific handling. [main.cpp](../choupi/src/main.cpp) reset clears transient arrays and native-session sidecars; it does not clear ordinary PIN fields. The native invocation PIN hooks in [bc_invoke.cpp](../choupi/src/jc_bytecodes/bc_invoke.cpp) publish SensitiveResult and do not establish a separate PIN state lifetime.

Consequences to reproduce: a validated persistent PIN can remain validated after reset; a failed check inside a transaction can have its retry decrement undone on abort. The existing producer-result assertions do not establish PIN lifecycle semantics. The exact currently generated ROM must also be matched to source before attributing on-image behavior.

**Needed:** implement these API guarantees through native VM state/dispatch as required by repository policy. Test wrong PIN + abort, successful check + reset, resetAndUnblock inside abort, cold restoration, and OwnerPINx variants. Do not implement this follow-up as a Java provider or altered CAP. Related owner: PROFILE-01 / CTX-03 / PERSIST-02.

### R05 — P1: failed persistent setters publish cache changes before storage succeeds

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** `JC_Instance::setField_Byte/Short/Int/Reference` in [jc_instance.cpp](../choupi/src/jc_types/jc_instance.cpp) updates the cached field before invoking the persistent storage helper. [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) can then fail while charging commit capacity, allocating a snapshot, serializing a reference, or writing the record.

If applet code catches that failure and continues or commits, the cache can expose a value that storage never accepted. Cache invalidation uses the rollback generation, so it does not repair a failed individual write followed by a successful commit. For a capacity error raised before the new snapshot is inserted, even a later abort may have no snapshot for that particular cache mutation. A reference setter can also replace `field.value` before resolving its target successfully.

**Needed:** publish cache state only after successful storage mutation, or restore it on every failed mutation. Validate scalar, two-word and reference writes with a caught failure, immediate read, commit, abort, GC and fresh restore; assert the old value and old reference roots remain canonical. Related owner: PERSIST-03.

### R06 — P1: instance field resolution does not verify the receiver's class

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** `resolveInstanceFieldToken()` in [bc_object_field.cpp](../choupi/src/jc_bytecodes/bc_object_field.cpp) receives the context, CP index and expected field kind, but no receiver. Callers resolve the instance independently and apply the returned flat offset. Descriptor-backed field-kind validation examines the **declaring** class; it does not prove the supplied receiver is an instance of that class/subclass.

A malformed CAP can combine a valid field reference for class A with an unrelated class B instance having a compatible slot. Bounds and stored-kind checks can both pass while the wrong object's field is read/written. This also warrants testing references to ROM API objects held by an applet; successful owner checks are not a substitute for class compatibility.

**Needed:** validate receiver assignability and relevant access rules before using the offset for every ordinary/wide/`_this` getter/setter. Cover unrelated classes with identical layouts, inherited fields, imported classes and native API object receivers. This is distinct from the already tracked Descriptor-free first-store kind gap. Related owner: HARD-01 / PROFILE-01.

### R07 — P1: several superclass walks can loop inside one native operation

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed missing bounds; hostile-CAP reachability requires regression.** [jc_class.cpp](../choupi/src/jc_handlers/jc_class.cpp) contains unbounded superclass walks in class-to-class `docheckcast()`, `getObjectClassFromAnObjectRef()` and `getInstanceFieldsSize()`. [bc_object_field.cpp](../choupi/src/jc_bytecodes/bc_object_field.cpp) has another unbounded superclass loop while flattening a field token. Some newer method/interface walks are capped at 256; those caps do not protect these other paths. Structural class parsing does not establish an acyclic superclass graph.

A self/two-class superclass cycle can wedge allocation, casting or field lookup inside a single bytecode handler. The per-instruction deadline is not checked inside these loops. Hardware can reach watchdog reset; PC execution can hang. Very deep valid-looking chains also require checked field-count accumulation.

**Needed:** one consistent bounded, cycle-aware class traversal policy used at load and runtime. Validate cycles and deep chains through allocation, casts, fields and method resolution, then prove manager recovery. Related owner: HARD-01.

### R08 — P1: Cipher operational byte arrays still have persistent/transactional lifetime

**7 November status:** concurrent source correction/partial correction is recorded in the status table above; the original defect description below is historical. Outstanding acceptance is not assumed complete.

**Source-confirmed.** [native_cipher.cpp](../choupi/src/native_cipher.cpp), `allocateByteArray()`, uses ordinary `heap.addArray(length, BYTE)`. `newCipher()` uses it for `IV`, `INITIALIV`, `BUFFERED` and the CTR stream-block slot; `ensureCapacity()` grows the buffer with the same allocator. The key workspace has a separate transient allocation fix, but these other arrays do not.

For a retained/persisted Cipher, these bytes go through normal persistent array writes. Native session counters now live outside transactions, while buffered input and IV changes can roll back. An update inside a transaction followed by abort can therefore leave a surviving count paired with reverted data/IV. Pending plaintext and CTR stream material can also remain in ordinary persistent records across reset, despite the initialized sidecar being cleared. Changing only operational counters did not complete the workspace lifetime change.

**Needed:** give the full operational workspace a consistent native transient, reset and transaction lifetime; inspect persisted records as well as return codes. Validate split update/final across abort, both small and grown buffers, CBC/CTR, warm reset and fresh restore. Related owner: PROFILE-01 / PERSIST-02; follow-up to RV-20261103-15, not a claim that its sidecar change is absent.

### R09 — P2: block-aligned update followed by an empty final call is rejected

**Source-confirmed.** In [native_cipher.cpp](../choupi/src/native_cipher.cpp), `updateSymmetric()` emits complete blocks and removes them from the input buffer. `doFinalSymmetric()` then rejects `dataLength == 0` for block ciphers. Thus AES/DES NOPAD `update(one block)` followed by `doFinal(empty)` throws `ILLEGAL_USE`, although the full message was block aligned. ISO9797 M1 can reach the same empty-buffer condition.

This is a normal multipart usage pattern. Tests of one-shot finalization and partial-block splits can pass while missing it.

**Needed:** track/process total operation semantics rather than treating an empty tail as an invalid whole message. Compare empty final, exactly one block in update, several full-block updates and partial tails against one-shot known answers; verify IV reset and subsequent reuse. Related owner: API-03 / PROFILE-01.

### R10 — P2: ISO9797 method-2 unpadding accepts an overlong padding suffix

**Source-confirmed.** `unpad()` in [native_cipher.cpp](../choupi/src/native_cipher.cpp) scans backwards through the **whole** plaintext for padding value 3, accepting a preceding `0x80` regardless of how many zero bytes follow it. It does not require the marker to be within the final block.

For AES, a two-block plaintext consisting of `80` followed by 31 zeros is accepted and shortened to zero, even though method-2 padding should add at most one block. This accepts malformed ciphertext padding and hides message-format errors. No padding-oracle exploit was tested or claimed.

**Needed:** constrain padding validation to the valid final-block suffix; include all-zero blocks, missing marker, marker one block too early, valid full-block padding, and wrong suffixes for AES and DES. Related owner: API-03 / HARD-01.

### R11 — P2: makeGlobalArray allocations have no evident reclamation path

**Source-confirmed retention; exhaustion rate not measured.** [jni.cpp](../choupi/src/jni.cpp), `makeGlobalArray`, allocates in the process-wide heap. [heap.cpp](../choupi/src/heap.cpp) stores strong pointers there; applet collectors skip global handles and refuse to collect the global heap. `clearGlobalArrays()` clears contents but retains allocations. `releaseGlobalArray()` exists for temporary RMI buffers and AID-construction cleanup; the public makeGlobalArray path does not arrange a release.

Repeated calls that discard their returned arrays can retain memory until process/device restart. Warm reset clears contents rather than reclaiming these arrays. The global allocation path also linearly scans all existing slots. This is separate from intentionally unsupported persistent-object deletion.

**Needed:** define reachability and ownership for public global-array lifetime and reclaim only when no permitted references remain. Measure thousands of allocate/drop/reset cycles with heap telemetry, while retaining one live array to prove its identity/data contract. Related owner: CTX-03 / PERSIST-01.

### R12 — P2: SCP03 rejects a valid no-data case-3 protected command

**Source-confirmed.** [scp03.cpp](../src/scp03.cpp), `verifyCommand()`, rejects lengths below 14, then accepts either `5 + Lc` or `6 + Lc` and permits an eight-byte MAC. A protected case-3 command with no plaintext data has `Lc=8` and total length **13**, so it is rejected before MAC verification. The equivalent case-4 command with Le has length 14 and can pass.

**Needed:** derive the minimum from the supported APDU cases rather than imposing the case-4 size. Test independently generated valid C-MACs for lengths 13/14, missing MAC, malformed Lc, maximum payload, failed MAC and a subsequent valid session. Existing successful GPPro exchanges do not test this edge. Related owner: GP-01.

### R13 — P2: VPCD read timeout is an inactivity timeout, not a frame deadline

**Source-confirmed.** [vpcd_protocol.cpp](../choupi/src/vpcd_protocol.cpp), `read_exact()`, passes the full `timeout_ms` to every poll after each successful short receive and EINTR. `read_message()` starts another full interval for the payload after the header.

A peer sending one byte per interval can keep an incomplete frame alive much longer than the nominal timeout, up to the declared payload length's worth of intervals. Current tests cover idle input and a stopped partial header, not a peer that keeps making slow progress. The initial restricted-context send failure is a separate test-environment result.

**Needed:** decide/document inactivity versus total deadline, and enforce a monotonic absolute deadline where a bounded frame is intended. Test slow-drip header/payload, EINTR and clean reconnect with measured upper bounds. Related owner: EMU-01.

### R16 — P2: branch validation rescans from method start on every taken branch

**Source-confirmed complexity; hardware cost unmeasured.** [pc_t.hpp](../choupi/src/jcvm_types/pc_t.hpp), `setBranchFromOffset()`, calls `is_instruction_start()` from [cap_instruction_boundaries.hpp](../src/cap_instruction_boundaries.hpp). That helper decodes sequentially from byte zero to the target each time. Taken branches near the end of a large method repeatedly pay for its prefix, including variable-width instructions.

This creates roughly O(iterations × prefix length) verification work for a small loop positioned late in a method. It can materially reduce applet throughput and increase deadline exposure even when loop work is constant. Bounds are useful and must remain; removing the check is not a valid optimization.

**Needed:** benchmark loops at increasing method offsets and consider a validated per-method instruction-start map/cache with correct package lifetime invalidation. Record RAM cost and APDU latency on the same image/profile. Related owner: HARD-01 / API-03.

### R17 — P2: stable-handle lookup and GC have adverse scaling

**Source-confirmed complexity; thresholds unmeasured.** Heap slots in [heap.hpp](../choupi/src/heap.hpp) are `List`, derived from `std::list`. [list.hpp](../choupi/src/jcvm_types/list.hpp), `at(index)`, walks from the beginning; [heap.cpp](../choupi/src/heap.cpp) uses it to resolve each handle. The mark walker also repeatedly scans all slots until no new edges are found. A reverse-order linked object graph can require many full passes; handle resolution adds further linear work.

GC is run on the physical post-APDU path, after the interpreter has returned, so expensive tracing also contributes host-visible response time beyond measured bytecode execution. The code favors allocation-free traversal, a valid memory tradeoff, but current evidence does not quantify the worst case or watchdog margin.

**Needed:** measure long chains in both allocation orders, wide graphs, sparse slot tables and repeated applet switching. Record GC wall time, maximum uninterrupted native interval, heap footprint and p95/p99 APDU latency before choosing indexed storage or bounded tracing work. Related owner: PERSIST-01 / API-01 / EMU-01.

### R18 — P2: Signature update is whole-message buffering with a 32,767-byte ceiling

**Source-confirmed.** [native_signature.cpp](../choupi/src/native_signature.cpp), `appendBytes()`, and the RSA/ECDSA append paths retain complete messages, grow buffers and reject totals beyond 32,767. Some paths allocate an additional whole-message vector before hashing/MAC. The supported-profile document explicitly discloses MessageDigest's 2,046-byte ceiling but does not similarly disclose this Signature ceiling.

Multiple update calls therefore do not provide unbounded streaming, and peak memory can include old/new workspaces plus vector copies and crypto state. Large-message support can fail well before mathematical algorithm limits on constrained RAM.

**Needed:** document cumulative limits and measured peak memory immediately; separately evaluate incremental hash/MAC state with correct reset/abort behavior. Test boundaries across APDUs, repeated reuse and failed growth. Preserve the existing disclosed digest limit rather than reopening it as an undisclosed new defect. Related owner: PROFILE-01 / API-01.

### R19 — P2: lengthy native copy/fill loops lack cooperative progress/deadline checks

**Source-confirmed missing callbacks; physical stall duration unmeasured.** The native Util intercepts in [bc_invoke.cpp](../choupi/src/jc_bytecodes/bc_invoke.cpp) copy/fill up to a short-sized length in one handler without cooperative progress calls. Persistent byte access in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) repeatedly restores/checks array metadata and performs backend operations; the PC path additionally prints selected byte writes. Several crypto copying/clearing loops have the same callback gap.

The interpreter services USB on an instruction interval and checks the deadline between bytecodes. That does not bound one expensive native handler. RSA key generation has dedicated progress callbacks, which do not establish a general native-operation guarantee.

**Needed:** measure maximum legal operations on nearly full storage and low-memory heaps; bound callback cadence in native long loops while preserving non-reentrancy and atomicity. Assert CCID progress and final response delivery, watchdog margin, and immutable overall deadline. Related owner: HOST-01 / HARD-01 / API-03.

### R22 — P1: ordinary object identity still depends on the first referencing field

**Source-confirmed.** The durable identity change in R02 of the older November 3 review was applied to arrays. Ordinary objects in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) still take `setPersistentTag(tag)` directly from the first reference field in `setPersistentField_Instance()`. A second reference writes an alias to that tag. Storing a new object in the first field serializes the new body over the old object's durable address.

Concrete sequence: persist object A with value `0x11` through field X; retain it through Y; replace X with new B containing `0x22`; restore through Y in a fresh heap. Y still names X's body address, which now contains B. Clearing X can likewise remove the header needed by A's aliases. Retained wrappers may temporarily hide the corruption through cached fields; their later writes still target the reused address.

There is an additional graph-sharing problem in the same serializer: its object-field case calls `setPersistentField_Instance(child_tag, child)` directly. A child already persisted at another tag is recursively written again unless it is currently active in the recursion guard. Two sibling references to the same child can consequently become separate serialized bodies, while the child's own mutation tag remains the first one. The recursion guard handles active cycles, not already serialized shared children.

**Needed:** use durable per-object identity for ordinary objects, and make every graph edge a reference to that identity. Test replacement, clearing, sibling sharing, diamonds, cycles, mutation through either alias, GC, abort and fresh restore; prove reference equality as well as values. Preserve applet root/owner semantics and migration behavior. Do not treat the passing array-retarget tests as object evidence. Related owner: PERSIST-01/02/03.

### R23 — P1: writing an object back to its own body field creates a self-alias

**Source-confirmed.** `setPersistentField_Reference()` in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) always writes an object alias when `instance->hasPersistentTag()` is true. It does not check whether the destination tag equals that persistent tag. `write_persistent_object_alias()` then replaces the object header with an alias pointing to itself.

An ordinary idempotent assignment such as `holder.object = holder.object`, where that field was the object's original body address, can therefore corrupt restoration. The object-alias reader requires its target to contain an object/proxy header; the self-target now contains an alias marker and fails that check. In-memory static roots or object caches can conceal this until fresh restoration.

**Needed:** preserve the body on same-identity assignments and prevent self/cyclic alias metadata from being published. Test both instance and valid aligned static reference fields, same-value writes within/without transactions, fresh restore and successful subsequent mutation. This is separate from R22's replacement/graph-sharing problem, although stable object bodies may address both. Related owner: PERSIST-02/03.

### R24 — P1: failed first persistence leaves an object permanently marked with an unpublished tag

**Source-confirmed.** `setPersistentField_Instance()` sets the instance's persistent tag and persistent flag **before** obtaining fields and writing its header/body. `JC_Instance::setPersistentTag()` in [jc_instance.cpp](../choupi/src/jc_types/jc_instance.cpp) retains that first tag permanently. A write/serialization exception does not remove it, and persistent-write rollback only restores filesystem records and advances a global generation.

### R25 — P2: JNI argument conversion can bypass SensitiveResult invalidation

### R29 — P2: native EC agreement leaks Mbed TLS allocations when C++ allocation throws

**Source-confirmed exception-safety gap; exhaustion rate unmeasured.** `generateSecret()` in [native_ec_key_agreement.cpp](../choupi/src/native_ec_key_agreement.cpp) initializes/populates raw `mbedtls_mpi` and `mbedtls_ecp_point` values, then allocates C++ vectors while those resources are live. **Needed:** use exception-safe ownership for every native resource and sensitive temporary. ### R30 — P2: hardware exception diagnostics assume every exception's first field is a short

### R31 — P1: an earlier rollback can erase a new object's fields on its first persistence

**Source-confirmed ordering/generation mismatch.** [jc_instance.hpp](../choupi/src/jc_types/jc_instance.hpp) initializes `persistent_fields_loaded=true` and `persistent_rollback_generation=0` for a new instance. ### R37 — P2: EC initialization and ECDSA require an optional cofactor

Independently, `loadAndValidateGroup()` in [native_ecdsa_signature.cpp](../choupi/src/native_ecdsa_signature.cpp) rejects `ECK != 1`, making otherwise valid named-curve ECDSA setup depend on the optional parameter. Non-cofactor agreement has a different path: `loadGroup(..., requireCofactor)` in [native_ec_key_agreement.cpp](../choupi/src/native_ec_key_agreement.cpp) gates K checking by algorithm. R28's rejection of an **inconsistent supplied** cofactor is distinct from this requirement that an optional value be supplied at all.

**Needed:** separate required key material from algorithm-specific cofactor requirements. Test public/private initialization and ECDSA with all required fields but no K, with the correct K, and with invalid supplied K; require DHC's missing-K error while preserving non-DHC behavior. Compare generated and manually populated keys. Related owner: API-03 / PROFILE-01.

### R38 — P2: key-pair generation silently replaces preinitialized parameters

`generateRsaPair()` in [native_ec_keypair.cpp](../choupi/src/native_ec_keypair.cpp) sets exponent 65537 unconditionally, then overwrites the public exponent component. `generateEcPair()` selects a group solely by key size and overwrites Field/A/B/G/R with that group's parameters. Neither path reads existing public parameters before generation. The checked-in [KeyPair contract](../choupi/javacard-sdk/javacard-api/src/javacard/security/KeyPair.java), `genKeyPair()`, requires a preinitialized RSA public exponent and preinitialized EC domain parameters to be retained, and invalid supplied parameters to be rejected.

An applet which sets an exponent before generating a pair therefore receives a different exponent without a corresponding parameter error. An unsupported or invalid preinitialized EC domain is silently replaced with the default rather than rejected. A named-curve-only implementation can reject unsupported domains; it still needs to inspect the supplied parameters instead of generating a different domain. Current probe code checks default exponent 65537, which does not exercise preservation.

**Needed:** validate and honor supported preinitialized public parameters; fail explicitly when they cannot be supported. Test default RSA and supported nondefault exponents, invalid exponents, retained supported EC domains and invalid/unsupported complete domains. Verify generated private/public consistency and read back parameters before and after generation, including repeated generation. Related owner: API-03 / PROFILE-01.

### R39 — P2: CBC MAC finalization preserves the nonzero IV for the next message

In [native_signature.cpp](../choupi/src/native_signature.cpp), parameterized MAC `init()` writes the supplied IV into `INITIALVECTOR`. `runMac()` reads that vector for each operation. Both successful `sign()` and normal `verify()` completion call `clearMacMessage()`, which clears buffered message bytes/count but leaves the IV unchanged. The next MAC on the same instance therefore uses the original nonzero IV again.

The checked-in [Signature contract](../choupi/javacard-sdk/javacard-api/src/javacard/security/Signature.java) says CBC AES/DES-family finalization resets the IV to zero. Existing tests include repeated messages with default zero IV and separate explicit-IV operations; those cannot distinguish retaining zero from resetting a supplied nonzero IV. CMAC rejects explicit IV parameters and is not the trigger described here.

**Needed:** implement finalization's CBC IV transition for sign and verify, including a false verification result, while preserving explicit reinitialization. Test two messages on the same object after nonzero-IV init: first against that IV, second against an independent zero-IV reference. Repeat after multipart update, failed verification and explicit nonzero-IV reinit. Related owner: API-03 / PROFILE-01.

### R40 — P2: card reset discards persistent-key crypto initialization instead of restoring it

[heap.cpp](../choupi/src/heap.cpp), `clearTransientArrays(CLEAR_ON_RESET)`, clears every instance's native-session fields. [jc_instance.cpp](../choupi/src/jc_types/jc_instance.cpp) makes absent sidecar getters return zero. Cipher initialization/mode and Signature initialization/mode/output length are stored only in those sidecars. [main.cpp](../choupi/src/main.cpp) invokes this clearing for selected and inactive applet contexts on reset; there is no corresponding restoration of the previous initialization configuration.

After a persistent-key Cipher or Signature is initialized and retained, logical reset followed by use without a fresh `init()` therefore reaches the initialized-zero check and throws `INVALID_INIT`. The checked-in [Cipher](../choupi/javacard-sdk/javacard-api/src/javacardx/crypto/Cipher.java) and [Signature](../choupi/javacard-sdk/javacard-api/src/javacard/security/Signature.java) class contracts require reset to restore the state established by the previous initialization, with CBC IV reset to zero. A transient key being cleared should invalidate its use; that does not justify discarding initialization for a still-valid persistent key. Existing transient-workspace rejection cases establish that narrower property only.

This differs from R08's persistent operational-byte/transaction problem and R36's physical callback mismatch: it is a loss of reusable API configuration at a reset boundary shared by the backends. **Needed:** distinguish retained initialization/key binding from discarded intermediate state, and reconcile both on logical reset and cold restore. Test persistent AES/DES Cipher and MAC, RSA/EC signatures, each after partial input then reset without reinit; compare with fresh initialized zero-IV/reference state. Check inactive applets too. Keep transient-key clearing fail-closed and verify factory metadata such as Signature output length remains correct. Related owner: CTX-03 / PROFILE-01 / PERSIST-02.

Extend R29's resource audit to `generateEcPair()`: raw `curveA` is live while `mpiBytes()` allocates a vector, before explicit `mbedtls_mpi_free()`. This is another source-confirmed instance of the same allocation-exception cleanup issue, not an additional finding. No low-memory rate, APDU latency, reset runtime outcome or cryptographic vector was measured in this pass.


## Fifth pass — APDU state transitions and invocation allocation failure

This source-only pass inspected APDU delivery/state, native exception dispatch and method-entry bookkeeping, alongside arithmetic/stack/return code. [Pass5 provenance](../artifacts/reviews/review_20261106/pass5/review-state.json) and source hashes record the inspected contents. No new tests, CAPs or implementation were written, and no runtime/build/hardware operation was performed. Arithmetic inspection found explicit wrapping helpers and masked unsigned shifts in the examined operations; this is not exhaustive bytecode acceptance evidence. The three additions below concern paths absent from the parser and APDUUtil helper checks.

### R41 — P2: receiveBytes ignores its state and offset contract

**Source-confirmed.** The checked-in [APDU.java](../choupi/javacard-sdk/javacard-api/src/javacard/framework/APDU.java), `receiveBytes(short)`, unconditionally returns zero. Its documentation requires `ILLEGAL_USE` before `setIncomingAndReceive()` and after an outgoing transition, and `BUFFER_BOUNDS` for negative offsets. Even `receiveBytes(-1)` returns normally. No native validation is reached by this body.

Buffering an entire short APDU before dispatch makes zero a reasonable result after valid reception; it does not remove state/argument checks. An applet relying on the defined error to distinguish misuse instead sees ordinary end-of-input, and `getCurrentState()` does not reflect any rejection. The implemented `receiveAPDUIncoming()`/`markAPDUIncomingReceived()` path in [jni.cpp](../choupi/src/jni.cpp) and [context.cpp](../choupi/src/context.cpp) validates the primary receive transition, but `receiveBytes()` bypasses it entirely.

**Needed:** enforce the receive API contract through the native VM boundary as required by repository policy, while retaining the fully buffered short-APDU model. Test before initial receive, after valid receive, after outgoing/full outgoing, negative and oversized offsets, zero remaining input, exact reason codes and a subsequent valid command. Passing parser fuzz or APDUUtil CLA tests cannot close this. Related owner: PROFILE-01 / HOST-01 / HARD-01.

### R42 — P2: outgoing length validation follows buffer capacity rather than the declared APDU contract

**Source-confirmed.** [context.cpp](../choupi/src/context.cpp), `setAPDUOutgoingLength()`, accepts any length up to its 1,022-byte response storage when chaining is enabled; it never checks the selected applet's ExtendedLength capability. The checked-in [APDU contract](../choupi/javacard-sdk/javacard-api/src/javacard/framework/APDU.java), `setOutgoingLength()`, requires `BAD_LENGTH` above 256 for an applet without that interface. The [declared profile](supported-profile.md) also excludes extended-length APDUs. Chaining short transport responses does not itself supply the missing API capability check.

There is a separate error-reason loss within the same validation path: a positive oversized length or a no-chaining length over the permitted bound throws the bare native `Exceptions::APDUException`. `dispatchJavaException()` in [bc_object.cpp](../choupi/src/jc_bytecodes/bc_object.cpp) maps every such enum to reason 1 (`ILLEGAL_USE`), including length errors which should be `BAD_LENGTH`. The Java wrapper does distinguish negative lengths with `BAD_LENGTH`, so reason behavior changes depending on which limit is crossed.

**Needed:** derive permitted lengths from the supported applet/API capability and chaining mode, independently of storage capacity, and preserve the specific reason through native dispatch. Test -1/0/252/253/256/257/1022/1023 with chaining on/off, valid and invalid state, and catch/read the Java reason. Clarify any intentionally supported long-response extension in the profile; do not claim ExtendedLength support merely because GET RESPONSE can split a buffer. Related owner: PROFILE-01 / HOST-01.

### R43 — P1: method-entry package bookkeeping can terminate on allocation failure

**Source-confirmed exception-containment gap; low-memory trigger not executed.** [context.cpp](../choupi/src/context.cpp), `Context::changePackageID()`, is `noexcept` and calls `packagesID.push_front()`. `packagesID` is [List](../choupi/src/jcvm_types/list.hpp), a public `std::list` subclass using its inherited allocating insertion. Allocation failure therefore calls termination rather than propagating to the interpreter's recovery boundary.

[JC method entry](../choupi/src/jc_handlers/jc_method.cpp), `callMethod()`, pushes the new frame and then calls this function for every method entry, including ordinary API calls. Even with stack space still available, the extra list-node allocation can fail under heap pressure. The catch-all in [interpretor.cpp](../choupi/src/interpretor.cpp) cannot contain an exception escaping a `noexcept` function. This is distinct from R01's opcode-fetch boundary and R02's incorrect unwind direction; fixing either does not make this allocation recoverable.

It also introduces allocation/free work on every interpreted call/return in addition to frame storage. The performance cost and failure incidence were not measured. **Needed:** make frame/package entry an exception-safe coherent operation with bounded or recoverable bookkeeping, and audit other allocating `noexcept` paths. Fault-inject failure specifically at package-list insertion after frame creation, verify caller/frame/package invariants, then execute a valid following APDU. Measure allocation count and method-heavy latency before selecting a representation; do not remove error containment to optimize it. Related owner: HARD-01 / CTX-01 / EMU-01.


## Sixth pass — transaction recovery and persistent-array validation cost

This source-only pass traced transaction journals, abort/commit cleanup, array persistence helpers and heap allocation against [FILESYSTEM_ABI](FILESYSTEM_ABI.md) and the checked-in JCSystem contract. [Pass6 provenance](../artifacts/reviews/review_20261106/pass6/review-state.json) records inspected hashes. The previous turn made progress by committing R41–R43; this pass adds four further findings. No implementation, test fixture or CAP changed. No proposed fault injection or runtime acceptance was executed, and all timing/capacity impact below remains unmeasured.

### R44 — P1: failed rollback discards the recovery journal and reopens ordinary writes

**Source-confirmed.** `rollback_persistent_writes()` in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) accumulates a failure flag when erasing new records or restoring old records fails, but continues, marks the transaction inactive, calls `fs_sync()` and unconditionally clears all saved snapshots. A subsequent abort sees no active transaction, while a new transaction is allowed. Commit-sync failure invokes this same rollback and discards its return value before reporting commit failure.

If one restoration fails, the resulting overlay can contain a mixture of old and transactional values. The function attempts to sync that mixture even after noticing the failure. On Pico, successful sync publishes the RAM overlay as a new durable snapshot, so the previous committed snapshot's protection does not by itself protect this path. A sync failure after otherwise successful restoration also loses the journal and pending-recovery state. API wrappers can report an error, but no sticky recovery/quarantine state blocks later APDUs or prevents a retry from appearing already complete.

The existing transaction test injects **one commit sync failure followed by successful rollback**; that is useful evidence for its case, not for failed rollback writes or repeated sync failure. **Needed:** retain recoverable state until restoration is established, or enter a defined state that prevents ordinary use until recovery/reset. Do not publish partial restoration. Inject failures at each rollback erase/write and at both commit and rollback sync, verify no mixed state is accepted or durably published, then test explicit retry and restart recovery. Related owner: PERSIST-03 / STORE-01 / HARD-01.

### R45 — P2: snapshot insertion failure leaves commit capacity charged without a snapshot

**Source-confirmed allocation-exception ordering.** `snapshot_persistent_tag()` in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) first calls `charge_persistent_snapshot(snapshot)`, which increments global `persistent_write_transaction_used_bytes`, and then calls `persistent_write_snapshots.push_back()`. Growing that vector can throw after the charge, before publishing the rollback entry. The local snapshot is destroyed without reversing the charge.

The record write occurs later, so this is not evidence that the unsnapshotted write succeeded. The defect is that a caught allocation failure leaves `getUnusedCommitCapacity()` smaller than the journal actually requires. Retrying can charge the same tag again, and unrelated valid writes can subsequently report buffer full. R05's object-field cache mutation is a different layer; correcting it does not reconcile this journal accounting.

**Needed:** make charging and snapshot publication one exception-safe operation, with unchanged accounting when publication fails. Inject vector-growth failure specifically after successful record read/charge, catch it, check remaining capacity and journal contents, retry the same tag and commit/abort. Cover new and existing records and failures after earlier successful entries. Existing array-allocation counters do not inject this vector-publication boundary. Related owner: PERSIST-02/03 / HARD-01.

### R46 — P2: persistent array element validation allocates a temporary array on every access

**Source-confirmed allocation work; latency impact unmeasured.** With `JCVM_SECURE_HEAP_ACCESS`, persistent byte/short/int/reference element helpers in [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) call `getPersistentField_Array()` to check type/size. That function constructs a new `shared_ptr<JC_Array>` and an owning tag buffer. It does not simply decode a small validated header or consult the already live array metadata.

For reference arrays, the restoring constructor in [jc_array.cpp](../choupi/src/jc_types/jc_array.cpp) additionally creates `reference_value_owners(length, sentinel)`. Thus reading even one element initializes an owner vector sized to the **entire array**, then destroys it after validation. Scanning N entries performs O(N²) owner-slot initialization through this validation layer, independently of the separate handle-lookup/GC scaling in R17. Primitive arrays do not allocate a full data copy in this constructor, but still incur per-access object/control-block/tag-buffer allocation. Allocation failure can turn a read of an existing valid array into an operation failure under heap pressure.

**Needed:** retain equivalent record/type/length checks with bounded metadata inspection rather than temporary owning array reconstruction. Measure primitive/reference scans at increasing lengths, allocator calls, peak temporary bytes and APDU latency on one image/profile; include low-memory reads and invalid/truncated records. Preserve security checks and owner provenance; merely disabling secure heap access is not an acceptable performance fix. Related owner: API-01 / PERSIST-01 / HARD-01.

### R47 — P2: transaction abort leaves references to newly allocated objects usable

**Source-confirmed lifecycle gap.** The checked-in [JCSystem abortTransaction contract](../choupi/javacard-sdk/javacard-api/src/javacard/framework/JCSystem.java) requires references to objects instantiated within an aborted transaction to become equivalent to null; it also describes forcing a reset/session lock when necessary for safe recovery. The current [native abort](../choupi/src/jni.cpp) only invokes persistent-record rollback. `beginPersistentWriteTransaction()` records no allocation epoch or heap frontier, and the [heap allocation paths](../choupi/src/heap.cpp) register no transaction-created handle set.

A local reference to an ordinary newly allocated object therefore survives a normal successful abort: no record rollback rewrites locals or changes that handle's identity/validity. The Java abort wrapper returns normally when the record rollback succeeds, and there is no session lock on that path. Reverting a persistent field that referred to the new object is insufficient when another reference remains in a local, transient array or other runtime root.

This differs from R24/R31's promotion/cache defects: it concerns a newly allocated object even when it was never serialized. **Needed:** define and implement transaction-created object invalidation or the documented safe session-reset alternative through native runtime state. Test allocation after begin, aliases in locals and transient arrays, abort, null comparison and attempted dereference; also test preexisting objects, successful commit and nested method/SIO returns. Verify handles cannot later be reused as a different live object through a stale reference. Related owner: PERSIST-02/03 / CTX-01 / HARD-01.


## Seventh pass — generic array utility API behavior

This source-only pass checked native utility entrypoints and static initialization code. Four additional findings concern the exposed ArrayLogic bridge. [Pass7 provenance](../artifacts/reviews/review_20261106/pass7/review-state.json) records native/API source hashes and the existing generated JNI header, which contains dispatch entries for all four generic copy/fill functions. That header was inspected, not regenerated; it is not fresh firmware acceptance evidence. No implementation, CAP, test or generated source changed. The proposed cross-type, failure and abort cases below remain unexecuted.

### R48 — P2: arrayCopyRepack rejects the cross-type conversions it is intended to perform

**Source-confirmed.** Both native repack entrypoints in [jni.cpp](../choupi/src/jni.cpp) call `copyArrayRange()`. The helper requires source and destination array types to be identical, checks both ranges using the same element count, and writes one destination element per source element. It throws `ArrayStoreException` for differing types.

The checked-in [ArrayLogic contract](../choupi/javacard-sdk/javacard-api/src/javacardx/framework/util/ArrayLogic.java) specifically supports byte/short/int packing and unpacking, high-order component first. For example, two bytes must form one short, while one int must form four bytes; destination bounds and the returned end offset depend on the converted element count. Even a valid two-byte-to-one-short request fails, and a one-element destination can be rejected before type checking because the helper treats source length as destination length. Same-type copying does not establish repacking support.

The helper also permits same-type booleans through `readArrayElement()` although ArrayLogic's defined primitive surface here is byte/short/int; reference input reaches `NotYetImplemented` rather than the defined utility error. **Needed:** implement and validate the supported conversion matrix in native code, correct converted range/return calculations, reject unsupported types and invalid packing multiples with the documented error. Cover all six cross-type directions, signed bit patterns, zero length, overlap for same-array copies, bounds and overflow before mutation. Related owner: PROFILE-01 / API-03.

### R49 — P2: atomic generic copy and fill have no standalone atomic transaction boundary

**Source-confirmed.** `arrayCopyRepack()` and `arrayFillGeneric()` in [jni.cpp](../choupi/src/jni.cpp) call element loops directly. There is no implicit transaction, capacity reservation, commit or failure rollback around them when the applet has no active transaction. [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp) snapshots an element's record only when a persistent-write transaction is already active, so these standalone calls bypass commit-capacity enforcement and have no journal protecting partially completed writes.

The checked-in [ArrayLogic contract](../choupi/javacard-sdk/javacard-api/src/javacardx/framework/util/ArrayLogic.java) requires atomic persistent destination updates and no copy/fill when commit capacity is exceeded. This is distinct from R48: a same-type operation with valid bounds still has the wrong atomicity boundary. Source inspection of the separate ordinary `Util.arrayCopy()` wrapper shows an explicit transaction path; its presence is not evidence for ArrayLogic's direct native calls.

No interrupted write or power-loss outcome was reproduced. **Needed:** give atomic generic operations a coherent native atomicity/capacity contract both outside and inside an existing transaction, without committing the caller's transaction. Test operations larger than remaining capacity, failure after each destination write, no partial change on rejection, caller catch/continuation, abort/commit and fresh restore. Keep physical power-loss validation separate. Related owner: PERSIST-02/03 / PROFILE-01 / HARD-01.

### R50 — P2: generic NonAtomic copy and fill participate in applet rollback

**Source-confirmed.** The `arrayCopyRepackNonAtomic()` and `arrayFillGenericNonAtomic()` entrypoints in [jni.cpp](../choupi/src/jni.cpp) call the same helpers as their atomic counterparts. `writeArrayElement()` uses ordinary `setByteEntry()`, `setShortEntry()` and `setIntEntry()`. For persistent arrays, those setters take snapshots in an active transaction.

Thus a NonAtomic generic fill/copy inside an applet transaction can consume commit capacity, throw buffer full and be undone by abort. Its checked-in [ArrayLogic contract](../choupi/javacard-sdk/javacard-api/src/javacardx/framework/util/ArrayLogic.java) requires bypassing the transaction facility even while one is active. The dedicated [byte non-atomic setter](../choupi/src/jc_types/jc_array.cpp) and ordinary Util interception in [bc_invoke.cpp](../choupi/src/jc_bytecodes/bc_invoke.cpp) already implement a different path; ArrayLogic does not reach it. Simply fixing R49 by wrapping the shared helper would make this distinction more important.

**Needed:** distinguish generic non-atomic writes through native storage dispatch and preserve their changes across an enclosing abort, including updating any preexisting rollback snapshot appropriately. Cover same-tag atomic-then-nonatomic and nonatomic-then-atomic sequences, byte/short/int, capacity exhaustion, overlap and fresh restore. Preserve atomic generic behavior separately. Related owner: PERSIST-02/03 / PROFILE-01.

### R51 — P2: native utility errors cannot be caught as the declared UtilException

**Source-confirmed.** Native ArrayLogic fill/compare/find validation in [jni.cpp](../choupi/src/jni.cpp) throws `Exceptions::UtilException` for unsupported primitive types or mismatched fill types. In [bc_object.cpp](../choupi/src/jc_bytecodes/bc_object.cpp), `dispatchJavaException()` has no case for that enum: it returns false without constructing/throwing a Java exception. The interpreter's enum catch in [interpretor.cpp](../choupi/src/interpretor.cpp) then follows its VM error/unwind path instead of executing an applet's matching Java catch handler.

The checked-in [UtilException API](../choupi/javacard-sdk/javacard-api/src/javacardx/framework/util/UtilException.java) defines distinct `ILLEGAL_VALUE` and `TYPE_MISMATCHED` reasons. The native sites use the same bare enum for both and have no reason channel. The remote-exception encoding table's awareness of UtilException does not supply local Java dispatch or the missing reason.

A valid negative API test which catches this expected exception can therefore fail the entire operation. **Needed:** map native utility failures to the proper runtime-owned Java exception with reason preservation. Test invalid array types and mismatched fill types under exact and superclass catches, assert reasons, then perform a valid operation in the same APDU and a subsequent APDU. Keep R48's wrong `ArrayStoreException` path distinct from this missing dispatch path. Related owner: PROFILE-01 / HARD-01 / CTX-01.

The generic copy helper also allocates a `uint32_t` vector for every source element, including byte copies; scratch size can be four times the byte payload before allocation overhead. Include this in R19/R46's native-loop and allocation measurements. No peak-memory or throughput number was measured, and no new performance claim is made from that source observation.

### R52 — P2: deselect-transient allocation does not check whether its applet context is selected

**Source-confirmed.** The checked-in [JCSystem contract](../choupi/javacard-sdk/javacard-api/src/javacard/framework/JCSystem.java), `makeTransient...Array()`, requires `SystemException.ILLEGAL_TRANSIENT` when CLEAR_ON_DESELECT is requested from a context other than the currently selected applet context. `getTransientClearEvent()` in [jni.cpp](../choupi/src/jni.cpp) checks only that the event code is reset or deselect; both primitive and object-array factories then allocate without testing selected-context identity.

This matters in the implemented SIO path: the selected client can invoke a service in an unselected server context, which executes through [main.cpp](../choupi/src/main.cpp) and the shareable dispatch. The server can successfully allocate a deselect-transient array even though its context is not selected. There is also no equivalent guard in the array constructor. Later clearing behavior does not supply the missing allocation-time rejection.

**Needed:** use a native selected-context predicate consistently for all transient factory types, preserving allowed same-context and CLEAR_ON_RESET cases. Test selected client A invoking service B, B allocating both event classes, same-package sibling contexts where applicable, selected/installation callbacks and invalid events. Assert exact SystemException reasons and a successful subsequent call. Related owner: CTX-03 / PROFILE-01 / HARD-01.

### R53 — P2: isAppletActive answers only for the executing applet's own AID

**Source-confirmed.** `isAppletActive()` in [jni.cpp](../choupi/src/jni.cpp) first rejects the executing context unless its current applet instance is active/installing, then compares the requested AID bytes only with `context.copyAppletAID()`. It never searches the selected instance or another applet's activity state. The checked-in [JCSystem API](../choupi/javacard-sdk/javacard-api/src/javacard/framework/JCSystem.java) defines the answer for the applet **specified by the argument**, active on this or another channel.

Even on the supported basic channel this is insufficient: client A remains selected while service B executes an SIO callback. B querying A's runtime AID should see A active, but the implementation either rejects B's inactive flag first or fails the AID equality check against B. An own-AID query in selected A and an inactive-other query in A both return plausible answers, so those existing probe patterns do not exercise the failing case. This finding does not request logical-channel support.

**Needed:** query actual registered/selected instance state by AID independently of the executing context. Test A querying self/B, B querying selected A during SIO, inactive and unregistered AIDs, select/install callbacks, reset and same-package sibling instances. Keep successful registration and currently selected activity distinct from merely executing service bytecode. Related owner: CTX-01/03 / PROFILE-01.

### R54 — P2: transient allocation limit failures report the wrong resource reason

**Source-confirmed deterministic size path; not executed.** In [jc_array.cpp](../choupi/src/jc_types/jc_array.cpp), `checkedBackingLength()` throws `FullMemoryException` when the backing size exceeds 65,535 bytes. For example, on an int-enabled profile a valid positive request for 16,384 transient ints requires 65,536 bytes and reaches this limit. The transient and global factories in [jni.cpp](../choupi/src/jni.cpp) catch that exception and set SystemException reason **5 (NO_RESOURCE)**. The checked-in [JCSystem factory contracts](../choupi/javacard-sdk/javacard-api/src/javacard/framework/JCSystem.java) specify **NO_TRANSIENT_SPACE** for unavailable transient space; the `std::bad_alloc` path already maps to that different reason, 2.

Thus the reason depends on whether unavailability came from the implementation's backing limit or the allocator. Applets catching the documented transient-space reason can mishandle the former even though both requests concern transient allocation. Persistent-storage NO_RESOURCE handling elsewhere is a separate contract and should retain its meaning.

**Needed:** map transient allocation unavailability consistently, including hard backing limits, with the documented reason. Test local and global transient factories at the per-type backing boundary, ordinary allocator exhaustion and negative lengths, on int-enabled/disabled profiles. Assert Java reasons and unchanged heap/registry state after failure; no algorithm or array-capacity expansion is needed to correct the reason. Related owner: PROFILE-01 / HARD-01 / CTX-03.

Extend R11's retention audit to the global AID cache: `addGlobalAIDObject()` strongly retains an object and retained byte array for each distinct AID. The inspected release calls are construction-failure cleanup; package forgetting clears foreign/global references but does not reclaim unreferenced historical AID cache entries. Repeated install/lookup/delete with distinct AIDs should be included in lifetime/lookup-cost measurement, while preserving still-live runtime AID references and required identity semantics. This is another runtime-owned retention case under R11, not a duplicate finding; no exhaustion rate was measured.

### R55 — P2: INSTALL preflight does not validate the dependency closure of loaded libraries

**Source-confirmed validation gap; three-package reproduction unexecuted.** `finishLoad()` in [cap_load.cpp](../src/cap_load.cpp) stores and enables a structurally accepted package without calling `validate_cap_imports()`. Inside `validate_cap_imports()`, each direct import is resolved and the current package's CP references are checked. It does not recursively validate each imported dynamic package's own imports or CP references. A library B can therefore be loaded while its dependency C is absent/incompatible; installing A which imports B can pass preflight when A's referenced B exports exist and B's superclass/method resolution does not otherwise traverse C. B's method body that references C is not checked by validating A's CP. The missing link is then discovered during execution rather than at acceptance of A's dependency graph.

This is narrower than claiming import version checks are absent. The [declared profile](supported-profile.md) requires installed dynamic packages' imports to be resolved, while [CAP trust documentation](CAP_EXECUTION_TRUST_MODEL.md) describes the direct install preflight. Libraries which never receive an applet INSTALL have no equivalent full import-validation step in this path.

**Needed:** establish readiness of the reachable dynamic dependency graph before declaring an applet executable, or validate/link libraries at an appropriate earlier publication boundary. Use bounded visited-state traversal and preserve supported load ordering. Test A→B→C with C missing, wrong version and present; include a B method that uses C only in its body, repeated/transitive imports and cycles with a defined policy. Require controlled rejection before applet install execution, then demonstrate corrected dependencies permit install. Existing deletion dependency coverage does not establish transitive linking readiness. Related owner: GP-01 / PROFILE-01 / HARD-01.

### R56 — P2: orphan cleanup repeats full storage walks for ordinary free package slots

**Source-confirmed avoidable work; elapsed cost unmeasured.** `clear_orphaned_dynamic_persistent_state()` in [cap_load.cpp](../src/cap_load.cpp) sets `has_orphans` when it finds any disabled package ID with no CAP bytes. That identifies a **free slot**, not evidence that orphan records exist. With spare dynamic capacity, normal LOAD, INSTALL, DELETE and restoration paths therefore enter cleanup even on an already clean store.

The cleanup loops over every free ID and calls `erasePersistentPackageState()` separately. [flashmemory.cpp](../choupi/src/jc_handlers/flashmemory.cpp), `snapshot_matching_persistent_tags()`, enumerates the store and filters for that package; [pico_filesystem.cpp](../src/pico_filesystem.cpp), `fs_erase_package_state()`, separately scans the overlay and calls compaction. With one of eight slots occupied, seven free IDs can each cause journal/enumeration/erase scans despite having no matching records. The physical overlay has 8,192 table slots. This is traversal work, not a claim of seven flash erases or seven durable snapshot writes: clean `fs_sync()` need not program flash.

The current-source cost grows with free IDs and storage/table occupancy and may repeat within a multi-step manager workflow. It is distinct from R17's heap lookup/GC scaling. **Needed:** measure scan counts and manager latency with 0/1/7 free slots and clean/orphaned sparse/dense stores; batch safe cleanup or retain a validated cleanliness state without weakening crash recovery. Include power-interrupted publication and package-ID reuse before relying on a shortcut. Report image/profile/storage occupancy with timings; no numerical speedup is established here. Related owner: STORE-01 / HOST-01 / PERSIST-03.

Extend R29's raw-resource cleanup audit to [native_rsa_math.hpp](../choupi/src/native_rsa_math.hpp): `rsaCrtModulus()` allocates its output vector while MPIs are live, and `rsaCrtModExp()` allocates exponent/output vectors before the explicit MPI frees. ### R58 — P2: the KeyPair constructor taking existing keys remains an unbound stub

### R59 — P2: foreign-array root routing can keep an unreachable cross-heap cycle alive

**Source-confirmed root over-approximation; cycle retention inferred, not runtime reproduced.** [Context root enumeration](../choupi/src/context.cpp), `visitRootReferences()`, asks `Heap::visitForeignArrayReferencesForPackage()` for incoming foreign references. In [heap.cpp](../choupi/src/heap.cpp), that registry walk visits every still-existing registered source array with foreign entries. It checks neither the source array's reachability from an applet/runtime root nor a coordinated cross-heap mark state. [JC_Array](../choupi/src/jc_types/jc_array.cpp), `visitForeignReferencesForPackage()`, emits its matching target handles as roots.

Consider two ordinary, not-yet-persistent Object arrays in different applet heaps: A[0] refers to B and B[0] refers to A, with explicit foreign owners. Such volatile foreign entries are allowed. After all real applet/stack roots to both arrays are dropped, collecting A sees B's registered entry as an incoming root and preserves A. Collecting B then sees A's entry and preserves B. Repeating per-heap collection does not break the cycle while both registrations remain. No live application root is required by this algorithm; the arrays keep each other registered/alive.

This can accumulate unreclaimable RAM graphs during repeated cross-applet work. One-way references from a reachable source must remain protected, so simply removing incoming foreign roots would introduce premature collection. This is different from R11's global allocation retention and R17's GC traversal cost: it concerns which **local** graphs are considered live.

**Needed:** distinguish registered cross-heap edges from actual root reachability, using a coordinated trace or another validated cross-heap lifetime strategy. Test two- and three-heap cycles and diamonds after dropping all application roots, repeated collection orders, and a rooted variant that must survive. Break edges, delete a package and test handle reuse; include both explicit helper roots and production Context enumeration. Establish CAP-path reachability using nested SIO argument handoff rather than assuming a server-local array can be returned directly (that return has separate wrapping restrictions). Record live/reclaimed objects and bounded RAM growth across repeated creation/drop, preserving owner collision isolation. The existing passing foreign-root test should remain positive coverage alongside these new cases. Related owner: PERSIST-01 / CTX-01 / HARD-01.

### R60 — P1: positive-depth dup_x duplicates the wrong stack segment

**7 November status:** source corrected by another session, with software closure reported; retain the original analysis below as historical evidence. See the status table above.

**Source-confirmed instruction semantics defect; static traces, no runtime reproduction.** [Oracle's Java Card 3.0.5 VM specification](https://docs.oracle.com/cd/E59935_01/JCVMS.pdf), §7.5.18, requires `dup_x` with positive N to duplicate the top M words and insert that copy N words down. Only M words are added. `bc_dup_x()` in [bc_stack.cpp](../choupi/src/jc_bytecodes/bc_stack.cpp) passes M/N directly to [Stack::dup()](../choupi/src/stack.cpp).

The helper instead starts at `TOS-(M+N)` and appends every word up to the old TOS, adding M+N words without the required insertion. It also requires M+N source words and that much spare capacity, rather than the instruction's source depth and M-word output growth. For `dup_x 0x12` (M=1,N=2), a valid two-word input `[10,20]` should become `[20,10,20]`; the helper rejects it for lacking three source words. With input `[1,10,20]` and sufficient capacity, its source-derived result is `[1,10,20,1,10,20]` instead of `[1,20,10,20]`.

There is another operand-boundary error in the same opcode: the int-enabled check requires `N < M+4`, excluding the specification's inclusive upper endpoint. Valid values such as M=1,N=5 are rejected before the helper. Zero-depth `dup`/`dup2` use N=0, where the current append loop happens to produce the intended behavior; successful tests of those forms conceal the positive-depth defect.

A valid CAP using this instruction can receive wrong primitive operands, altered reference ordering, unexpected overflow or later type errors; bounds-safe instruction decoding does not establish correct execution. **Needed:** implement the defined insertion with correct source/output word counts and inclusive operand limits while preserving each word's type/owner metadata and complete int pairs. Test every legal M/N form and each invalid form with exact stack values/depth, sufficient and insufficient input/capacity, references with foreign owners and int combinations. Run complete bytecode execution as well as the Stack helper, then verify caught failure recovery and a following APDU. Extend existing R03 pointer-range safeguards rather than forming out-of-array pointers during these checks. Related owner: HARD-01 / PROFILE-01 / CTX-01.
